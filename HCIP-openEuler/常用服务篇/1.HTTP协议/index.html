    1.HTTP协议

    1.万维网

    1.1.万维网的定义

    万维网（World Wide Web,WWW/Web）是一个由无数通过互联网连接的超文本文档和其他资源组成的全球性巨大信息空间。使用户能够在全球范围内共享和获取信息。我们平时访问的各种网页资源都是运行（依赖）在万维网上的。

    打个比方，互联网相当于道路提供了最基础的网络连接和承载能力，万维网像是一个建造在互联网上的购物中心，这个购物中心里有各种类型的店铺（网页资源）。

    在平常浏览器上访问的网址上呈现的www是一个标识，代表加入了万维网。

    1.2.万维网的组成

    万维网的运作依赖于经典的C/S模型和几个核心技术的协同工作。

    1. URL：资源的地址，https://www.baidu.com这就是一个URL，告诉浏览器去哪里找到资源。
    2. HTTP：协议，交流的语言
    3. 浏览器按照HTTP协议，将你的请求打包，通过互联网发送到指定的Web服务器。
    4. 服务器处理请求后，再按照HTTP协议，将请求的网页内容（HTML代码、图片等）返回给浏览器。
    5. HTML：服务器返回的主要是HTML文档。HTML用标签定义了网页的机构和内容。
    6. 浏览器：浏览器接收到HTML、CSS、JavaScript后，会解析这些代码，并将其渲染成我们看到的直观、美观的网页。

    总结：客户端通过浏览器访问指定URL，浏览器通过网络向目标服务器发送HTTP请求，服务器在收到请求后将资源通过HTTP响应发送给客户端浏览器。服务器发送的资源是一系列代码，最终由客户端浏览器通过编译得到网页。

    1.3.资源定位符

    在我们使用万维网的过程中，我们需要有一种方式帮助我们定位到资源的位置，类似于“门牌号”、“地址”的概念。在互联网中“资源的地址”叫做URI。

    1.3.1.URI

    URI(Unifrom Resource Identifier)统一资源标识符，用于唯一标识一个抽象或物理资源。URI是一种统称，其包含了URL和URN，它们是URL的两种不同实现策略。

    • URL：通过“地址”来标识。
    • URN：通过“名字”来标识。

    1.3.2.URL

    URL(Uniform Resource Locator)统一资源定位符，用于指明资源的位置和访问方式。

    结构：scheme://[user:password@]host[:port]/path[?query][#fragment]

    • scheme：协议（如何访问），如https、http、ftp等。

    • host：主机名（定位资源），域名或IP地址。

    URL的方式更像买东西，你需要知道“店员”的名字么？？你只需要知道商铺的位置，以及你怎么过去就可以了。

    1.3.3.URN

    URN(Uniform Resource Name)统一资源名称，在全局范围内为资源提供一个唯一、持久、与位置无关的名称。URN类似于每个人的名字和身份证，即使资源的位置（URL）改变了，它的URN也应该保持不变。

    URN本身不支持资源请求和响应的功能，也就意味着你不能直接在浏览器里输入URN来获取资源。它可以被使用在分布式存储的场景里，此时无所谓请求的资源在哪个服务器上存储，通过URN进行资源的请求后，会由最近的拥有这个资源的服务器进行回应。

    结构：urn:<命名空间标识符>:<命名空间特定字符串>

    • 例子1（图书）：urn:isbn:0451450523（标识了一本特定的书《银河系漫游指南》）
    • 例子2（UUID）：urn:uuid:6e8bc430-9c3a-11d9-9669-0800200c9a66（用一个全局唯一ID标识某个资源）
    1.3.4.区别总结

    举个例子，现在你要买一款华为手机，用URL的表达方式是你以华为某线下门店作为你的目的地，直接过去购买。用URN的表达方式是，你直接在某东搜索华为手机直接购买下单，那么理所当然的会从距离你最近的仓库进行发货。

    2.HTTP协议

    HTTP超文本传输协议是万维网的基础通信协议，用于客户端（浏览器）与服务器之间的通信。HTTP是一种无状态的应用层协议，最初设计用于传输HTML文档，但现在已扩展为支持多种类型的数据，这使得用户可以在万维网上请求各类资源，如：网页、图片、视频、音频、文档等。

    简单来说HTTP协议是用于在万维网上请求获取目标资源的方式。可以把平时访问网页的动作看成“存储”，万维网上获取的资源可以是代码、图片、视频等等，本质上和“文件共享”没有太大的区别，那HTTP协议的作用也和FTP、Samba差不多了。

    客户端与服务器之间通过交换一个个独立的消息进行通信，由于HTTP协议本身是无状态应用层协议，所以它是没有“记忆”的。这是为了更快的处理大量事务，确保协议的可伸缩性，而特意把HTTP协议设计成如此简单的。

    由客户端发出的消息被称作请求（request），由服务端发出的应答消息被称作响应（response）。通常由HTTP客户端发起一个请求，创建一个到服务器指定端口（默认80）的TCP连接。HTTP服务器则在80端口监听客户端的请求。一旦收到请求，服务器会向客户端返回一个状态，比如HTTP/1.1 200 OK，以及客户端请求的内容，如文件、网页等。

    2.1.HTTP协议的架构

    2.1.1.C/S架构

    客户端/服务器架构，客户端为用户提供本地操作界面，向服务器发送请求，并处理服务器返回的结果。服务器负责管理资源（数据、文件等），处理客户端的请求，并提供服务。

    而对于典型的C/S架构除了是由客户端主动向服务器发送请求，服务端被动回应之外，还需要用户的终端上安装客户端软件。而对于开发人员来说不同的系统都需要独立的开发一款软件，相对来说比较麻烦。

    2.1.2.B/S架构

    浏览器/服务器架构，是C/S架构的一种改进。它将客户端统一为通用的网页浏览器，将应用的核心功能集中在服务器端实现。比如平常各种应用的网页版、谷歌百度等网站。包括小程序的设计思想也非常接近B/S架构（无需安装，即点即用）。

    从最根本的角度来看，HTTP协议严格遵守C/S（客户端/服务器）模型。

    • 客户端：主动发起连接和请求的一方，在HTTP中这通常是浏览器，但也可能是手机APP、爬虫脚本、API调用工具等。
    • 服务器：被动等待请求并提供服务的一方。在HTTP中，这就是Web服务器，如Nginx、Apache等。

    HTTP协议规范本身只定义了“请求方”和“响应方”之间的对话规则，它并不关心请求方式浏览器还是其他软件。但HTTP协议一问一答的模式是典型的C/S交互。

    2.2.HTTP工作原理

    HTTP协议定义Web客户端如何从Web服务器请求Web页面，以及服务器如何把Web页面传送给客户端。HTTP协议采用了请求/响应模型。客户端向服务器发送一个请求报文，请求报文包含请求的方法、URL、协议版本、请求头部和请求数据。服务器以一个状态作为响应，响应的内容包括协议的版本、成功或者错误代码、服务器信息、响应头部和响应数据。

    1. HTTP客户端与Web服务器的指定端口建立一个TCP套接字连接。
    2. HTTP客户端向Web服务器发送一个HTTP请求报文，请求报文由请求行、请求头部、空行和请求数据组成。
    3. Web服务器解析请求，定位请求的资源位置。服务器将资源“副本”放入HTTP响应报文发送给客户端。响应报文由状态行、响应头部、空行和响应数据组成。
    4. 若connection模式为close，则服务器主动关闭TCP连接，客户端被动关闭连接。若connection模式为keepalive，则该连接保持一段时间，在改时间内可以继续接收请求。
    5. 客户端浏览器解析响应报文中的状态行，查看请求是否成功。随后客户端解析收到的HTML代码等资源，将其编译处理后在浏览器中显示。

    2.3.缓存

    浏览器会自动将访问过的资源存储在本地，这个过程叫做缓存。但它和你主动保存一个文件完全不同。缓存的目的是提升性能和节省带宽。

    当第一次访问一个网站时，浏览器会：

    1. 下载所有资源（HTML、CSS、JS等）。
    2. 在后台，自动将这些资源的一份副本保存在硬盘上一个特定的文件夹里（缓存目录）。

    当再次访问同一个网站时，浏览器会：

    1. 首先检查本地缓存里是否已经有这个资源。
    2. 如果有，它会向服务器问一句：这个资源自从我上次下载后，有变化么？
    3. 如果服务器回复“没变化”（状态码304 Not Modified），浏览器就会直接从本地缓存加载资源，速度极快。
    4. 如果服务器回复“有变化”，浏览器才会重新下载新版本。

    所以，当我们第二次访问一个网页时能飞快加载是因为缓存。

    矛盾：

    你可能会觉得缓存是不是和无状态有一点冲突呢？实际上缓存就是为了解决无状态的一部分问题的。

    无状态有一个非常大的缺点：每个请求都必须包含完整信息，这可能导致重复传输大量相同的数据。缓存就是为了解决这个缺点而生的。

    2.4.长连接与短链接

    HTTP协议是应用层协议，它依赖于传输层的TCP协议进行可靠传输。而一个完整的TCP会话需要通过“三次握手”建立TCP连接，通过“四次挥手”来关闭TCP连接，这两者都是耗时的过程。

    因此，HTTP长连接与短连接的本质，就是决定一个TCP连接是只为一个HTTP请求/响应服务，还是可以为多个HTTP请求/响应服务。

    2.4.1.短连接

    短连接是HTTP协议最初默认的行为。

    工作流程：

    对于每一个HTTP请求，都会经历以下步骤：

    1. 建立TCP连接：客户端与服务器进行三次握手。
    2. 发送HTTP请求：客户端通过建立的连接发送请求报文。
    3. 服务器处理并返回响应：服务器处理请求，并返回响应报文。
    4. 关闭TCP连接：客户端与服务器进行四次挥手，断开连接。

    如果页面需要加载多个资源（如CSS、JS、图片），那么每个资源的请求都会重复上述四个步骤。

    特点：

    • 优点：实现简单，对服务器来说，管理方便，不会占用长期资源。

    • 缺点：

    • 性能极差：每个请求都需要建立和关闭连接的额外开销，网络延迟（RTT， 往返时间）大大增加。
    • 资源浪费：频繁的 TCP 连接和断开消耗大量的 CPU 和内存资源（客户端和服务器都需要）。
    2.4.2.长连接

    为了解决短连接的巨大性能问题，HTTP/1.1默认采用了长连接（也称为持久连接）。

    工作流程：

    1. 建立TCP连接：客户端与服务器进行三次握手。
    2. 多次HTTP通信：
    3. 客户端发送第一个请求。
    4. 服务器返回第一个响应。
    5. 连接保持打开状态。
    6. 客户端可以继续在此连接上发送第二个、第三个....请求。
    7. 关闭TCP连接：当一端（通常是客户端）决定不再需要发送请求，或者连接空闲时间超过一定阈值后，才会发起四次挥手关闭连接。

    优点：避免了每次请求都需要重新建立连接的开销，适合频繁交互的数据传输。

    缺点：长时间占用连接可能导致服务器资源的浪费（特别是在高并发场景中）。

    2.5.HTTP请求方法

    HTTP请求方法指明了客户端希望服务器对指定资源执行的操作类型。它们是HTTP协议的核心，定义了请求的意图。

    1. GET
    2. 用于请求指定的资源。GET请求只应用于获取数据，不应产生其他副作用（如修改数据）。
    3. 特点：
      • 多次执行相同的GET请求，服务器状态不会发生变化。
      • 多次执行相同的GET请求，返回的结果应该相同。
      • 请求参数通过URL的查询字符串（Query String）传递。例如?key1=value&key2=value2
    4. POST
    5. 用于提交数据到服务器，通常会导致服务器状态的变化。例如提交表单、上传文件等。

    6. 特点：

      • 每次提交都会改变服务器状态。
      • 多次提交相同的 POST 请求可能会产生不同的结果（例如，创建两个内容相同但ID不同的订单）。
      • 请求参数通常放在请求体（Body）中，格式可以是 application/x-www-form-urlencoded, multipart/form-data, application/json等。
      • 数据在 URL 中不可见，相对更安全（但仍是明文，真正的安全需要 HTTPS）。

    7. PUT

    8. 用于完整更新指定资源。客户端提供更新后的完整资源信息。

    9. 特点：

      • 会改变服务器状态。
      • 多次执行相同的 PUT 请求，服务器状态与执行一次的结果相同。例如，多次将用户姓名更新为“Alice”，结果始终是“Alice”。
      • 例如：更新用户ID为123的完整个人信息。

    10. PATCH

    11. 用于部分更新指定资源。客户端只需要提供需要更新的那部分字段。

    12. 例如：只更新用户的手机号码，而不影响其他信息。

    13. DELETE

    14. 用于删除指定的资源。
    15. HEAD

    16. 与GET方法类似，但服务器只返回响应头，不返回资源的文本部分。使用这个方法可以在不必传输全部内容的情况下，就可以获取其中关于该资源的信息（元数据）。

    17. OPTIONS

    18. 用于查询服务器针对特定资源所支持的请求方法。
    19. TRACE
    20. 沿着到目标资源的路径执行一个消息回环测试。主要用于诊断和测试。
    资源操作 常用方法 描述
    查询集合 GET /articles 获取文章列表
    创建新资源 POST /articles 创建一篇文章
    查询单个资源 GET /articles/123 获取ID为123的文章
    完整更新资源 PUT /articles/123 完整更新ID为123的文章
    部分更新资源 PATCH /articles/123 只更新文章123的标题
    删除资源 DELETE /articles/123 删除文章123

    2.6.HTTP状态码

    HTTP状态码是服务器在响应客户端请求时返回的三位数字代码，用于告知客户端（浏览器）当前的请求是成功了、失败了，还是发生了什么情况。

    状态码的五个类别：

    成功类：

    • 200 OK：表示请求成功。这是最理想的状态。
    • 当你正常打开一个网页或成功提交一个表单后，通常会返回200。

    重定向类：

    • 301 Moved Permanently永久移动：请求的资源已经永久移动到新的URL。浏览器会自动跳转到新地址，并且搜索引擎会将就地址的权重转移到新地址。

    • 网站改版，更换了域名或目录结构。例如，从http://example.com永久重定向到https://example.com

    • 302 Found临时移动：请求的资源临时从不同的URL响应。浏览器会跳转，但搜索引擎会保留源地址。

    • 304 Noot Modified：用于缓存。告诉浏览器，它本地缓存的版本仍然是最新的，可以直接用缓存的，不用重新下载。

    • 刷新页面时，如果页面内容没变，服务器会返回304，从而加快加载速度。

    客户端错误类：

    • 400 Bad Request错误请求：服务器因为请求的语法有误，无法解决。

    • 例如，前端提交的数据格式错误，比如JSON格式不正确。

    • 401 Unauthorized未授权：客户端请求需要用户认证（需要登录）。

    • 403 Forbidden禁止访问：服务器理解请求，但拒绝访问。客户端没有权限访问这个资源。

    • 例如，尝试访问服务器上禁止访问的目录，或IP被拉黑。

    • 404 Not Found未找到：服务器找不到请求的资源。

    • 例如，输入了错误的URL，或网页已被删除。

    服务器错误类：

    • 500 Internal Server Error服务器内部错误：服务器遇到了一个未曾预料的状况，导致它无法完成对请求的处理。通常是服务端代码BUG。

    • 例如，网站的后端程序（如PHP、Python、Java）出错了。

    • 502 Bad Gateway错误的网关：作为网关或代理的服务器，从上游服务器收到无效响应。

    • 当你的请求需要经过一个服务器（如Nginx）去访问另一个服务（如PHP-FPM）时，如果后端服务挂了或未响应，Nginx就会返回502。
    • 503 Service Unavailable服务不可用：服务器当前无法处理请求（由于过载或进行停机维护）。这通常是临时状态。
    • 例如，网站进行维护，或访问人数太多服务器忙不过来。
    • 504 Gateway Timeout网关超时：作为网管或代理的服务器，未能及时从上游服务器收到响应 。
    • 与502类似，但504特指超时。即后面的服务处理时间太长，前面的网关等不及了。

    2.7.HTTP请求格式

    请求行：这是报文的第一行，包含了最核心的三个信息。

    • 方法：表示客户端希望服务器执行的操作。

    • 请求目标：通常是URL的路径部分，指明请求的资源在服务器的哪个位置。例如/index.html。

    • HTTP版本：声明使用的HTTP协议版本，如HTTP/1.1或HTTP/2。

    • 示例：GET /index.html HTTP/1.1，表面客户端想用HTTP/1.1协议，通过GET方法获取服务器更目录下的index.html文件。

    请求头：以key:value的形式组成的多行文本，为服务器提供关于这次请求的额外信息。用于定义客户端的能力、偏好以及请求的上下文。

    • Host：（必需，特别是在 HTTP/1.1 中）指定请求的服务器的域名和端口号。因为一个服务器可能托管了多个网站，需要这个头来区分。
    • Host: www.example.com
    • User-Agent：告诉服务器客户端的软件信息（浏览器类型、版本、操作系统等）。服务器可以根据这个信息返回不同的内容（如为手机返回移动版页面）。
    • User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ...
    • Accept：告诉服务器客户端能够处理哪些类型的响应内容（MIME 类型）。
    • Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
    • Content-Type：（主要用于 POST、PUT 等方法）声明请求体中数据的媒体类型。
    • Content-Type: application/json（表示提交的是 JSON 数据）
    • Content-Type: application/x-www-form-urlencoded（表示提交的是表单数据）
    • Content-Length：声明请求体的字节大小。
    • Content-Length: 348
    • Authorization：包含用于验证客户端身份的凭证，例如 Bearertoken 或基本的用户名密码。
    • Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
    • Cookie：将之前服务器通过 Set-Cookie头设置的 cookie 发送回服务器，用于维持会话状态（如保持登录）。
    • Cookie: sessionId=abc123; username=john_doe
    • Referer：表示这个请求是从哪个页面链接过来的。常用于分析流量来源和防盗链。
    • Referer: https://www.google.com/

    请求体：

    请求体是跟在请求头之后的一个空行后面的部分。不是所有请求都有请求体，比如GET、HEAD、DELETE请求通常没有。它主要用于包含要发送给服务器的数据。

    场景：

    • 提交表单：当用户填写用户名、密码并点击提交时，这些数据就放在请求体中。
    • 上传文件：文件内容作为请求体发送。
    • API调用：向服务器发送JSON或XML格式的数据。

    2.8.HTTP响应格式

    状态行：

    • HTTP版本：服务器使用的HTTP协议版本，如HTTP/1.1
    • 状态码：三位数字代码，表明请求的成功或失败。
    • 状态短语：对状态码的简短文字描述，便于理解。

    响应头：

    和请求头类似，响应头也是由key:value组成的多行文本。

    • Content-Type：最重要的头之一，声明响应体中数据的媒体类型（MIME类型），这样浏览器才知道如何解析数据（是当作HTML渲染，还是当作图片显示，还是当作JSON处理）。
    • Content-Type: text/html; charset=UTF-8
    • Content-Type: image/png
    • Content-Type: application/json
    • Content-Length：声明响应体的字节大小（长度）。这有助于浏览器知道数据是否已经接收完整。
    • Content-Length: 1024
    • Set-Cookie：服务器通过这个头向客户端（浏览器）设置Cookie，浏览器会保存这些Cookie，并在后续对同一服务器的请求中通过 Cookie请求头发送回去，用于会话管理。
    • Set-Cookie: sessionId=abc123; expires=Wed, 21 Oct 2025 07:28:00 GMT; path=/
    • Cache-Control：指示客户端和中间代理（如CDN）应该如何缓存这个响应。这对于网站性能至关重要。
    • Cache-Control: max-age=3600（表示响应可以缓存1小时）
    • Cache-Control: no-cache（表示需要先验证资源是否已更新）
    • Cache-Control: no-store（表示禁止缓存任何部分）
    • Server：描述服务器使用的软件信息（如Nginx、Apache）。出于安全考虑，生产环境有时会隐藏或修改这个头。
    • Server: nginx/1.18.0
    • Location：主要用于重定向响应（状态码为3xx）。它的值是一个URL，告诉客户端应该自动跳转到这个新地址。
    • Location: https://www.new-example.com/new-page（通常配合 301 Moved Permanently或 302 Found状态码）
    • Date：响应报文生成的日期和时间。
    • Date: Tue, 15 Oct 2024 08:12:31 GMT

    响应体：

    响应体包含了服务器返回给客户端的实际数据。不是所有响应都有响应体，比如对HEAD方法的响应就没有。

    常见内容：

    • 当请求一个网页时，响应体是HTML代码。

    • 当请求一个CSS文件时，响应体是CSS代码。

    • 当请求一个API接口时，响应体通常是JSON或XML数据。

    • 当请求一张图片时，响应体是图片的二进制数据。

    2.9.HTTP的版本

    HTTP/0.9（1991）：

    这是HTTP的最初版本，只有一个方法GET，没有请求头和响应头。服务器响应后，立即关闭TCP连接。功能太单一，无法传输其他类型的数据，没有状态码，无法进行复杂的交互。

    HTTP/1.0（1996）：

    这是第一个得到广泛使用的版本，引入了大量现代HTTP的核心概念。

    引入了请求头和响应头，允许传输更多元数据，如Content-Type（可以传输HTML、图片、文件等）、Content-Length、User-Agent、Status Code等。加入了持久连接。

    HTTP/1.1（1997-1999）：

    加入了持久连接，强制要求Host请求头使得同一个IP地址的服务器可以托管多个域名（虚拟主机）。引入了更多方法PUT、PATCH、DELETE、OPTIONS、TRACE。

    HTTP/2（2015）：

    HTTP/2的目标是显著提升网页加载速度。它没有改变HTTP的语义，而是改变了数据格式的传输方式。通常，HTTP/2要求基于HTTPS（加密）。

    HTTP/3（2022）：

    弃用了TCP协议，转而使用基于UDP的QUIC协议。

      1. 基于QUIC协议：QUIC在用户空间实现，整合了TCP的可靠性和TLS的安全性，但比TCP更灵活、部署更快。
    • 解决TCP队头阻塞：这是HTTP/3最大的优势！QUIC在传输层原生支持多路复用，每个数据流是独立的。单个数据流的包丢失只会影响该流，不会阻塞其他所有流。
    • 更快的连接建立：QUIC将加密和连接建立合并，通常只需1次往返（0-RTT或1-RTT）就能建立安全连接，而TCP+TLS需要2-3次往返。这极大降低了延迟。
    • 连接迁移：当网络切换时（如Wi-Fi切到5G），基于IP和端口的TCP连接会中断需要重连。而QUIC使用连接ID，网络切换后连接依然保持。
    • 现状：正在快速普及中，被主要浏览器（Chrome, Firefox, Edge, Safari）和大型云服务商/网站（Google, Cloudflare, Akamai等）支持。是未来的明确方向。

    当前大部分网站主流的依旧是HTTP/1.1版本，这是因为升级所需要的成本和复杂性非常高。即使服务器和网络链路支持高版本，但如果链路中的任何一环（如某个网络代理或客户端）不支持，系统会自动降级使用HTTP/1.1/这种向后兼容性使得支持新协议更像一个性能增强选项，而非必须项。

    3.HTTPS

    3.1.明文传输

    在HTTP协议中，客户端与服务端的数据都是以明文的方式在互联网中传输的。假设你要在网页上登录淘宝或支付宝等重要软件，若是HTTP协议你的账户和密码都会以裸奔的形式传输给服务端。攻击者可以很轻易的获取你的账户与密码，盗用你的账户。

    HTTPS协议就是为了保证传输过程中的数据以密文形式传输，且对你访问的网站进行最基本的验证，验证其身份是否可信。所以目前你访问的网站基本都是以https开头的。

    3.3.SSL框架

    SSL(Security Socket Layer)安全套接层，是一种在客户端和服务器之间建立安全通道的协议，是Netscape公司提出的基于web应用的安全协议，它为基于TCP/IP连接的应用程序协议（如HTTP、Telenet、FTP等）提供数据加密、服务器认证、消息完整性以及可选的客户端认证。SSL协议具备如下特点：

    • 所有要传输的数据信息都是加密传输，第三方无法窃听。
    • 具有校验机制，信息一旦被篡改，通信双方会立刻发现。
    • 配备身份证书，防止身份被冒充。

    SSL协议自1994年被提出以来一直在不断发展。Netscape公司发布的SSL2.0和SSL3.0版本得到大规模应用。而后互联网标准化组织基于SSL3.0版本推出了TLS1.0协议（又称SSL3.1），之后又推出了TLS1.1和TLS1.2版本。

    3.3.1.SSL的报文结构

    SSL协议结构分为两层，底层为SSL记录协议，上层为SSL握手协议、SSL密码变化协议、SSL警告协议。

    • SSL握手协议：用于在实际的数据传输开始前，通信双方进行身份认证、协商加密算法、交换加密密钥等。相当于完成所有传输准备工作。

    • SSL密码变化协议：这个协议只包含一条消息（ChangeCipherSpec）。客户端和服务器双方都可以发送，目的是通知对方后面发送的数据将启用新协商的算法和密钥。

    • SSL记录协议：建立在可靠的传输协议之上，负责把上层的数据分块进行。

    3.3.2.对称加密

    在SSL中引入了会话密钥的概念。客户端与服务器采用公钥和加密算法协商出会话密钥，后续的数据报文都使用此会话密钥进行加密和解密（即对称加密算法）。对称加密算法速度很快，这样就大大提升了加解密运算效率。这里使用到的密钥实际上就是共享密钥，叫做会话密钥是因为引入了Session的概念，就是基于TCP的SSL每个连接与一个会话相关联，会话由SSL握手协议来创建，为每个连接提供完整的传输加密，即握手过程包含在会话之中。

    3.3.3.非对称加密

    公钥加密私钥解密，私钥加密公钥解密

    从上文可得出，SSL连接的建立，主要依靠SSL握手协议。其核心设计思路为采用公钥加密进行密文传输。SSL协议采用非对称加密算法，服务端会提前生成一对公私钥并将公钥告诉客户端，然后客户端用服务器的公钥加密信息，服务器收到密文后，用自己的私钥解密。

    非对称加密工作原理：

    1. 客户端A要向服务器B发送信息，B要产生一对用于加密和解密的公钥和私钥。
    2. B的私钥自己保密，B的公钥告诉A。
    3. A要给B发送信息时，用B的公钥加密信息。

    4. B收到这个信息后，自己的私钥解密。其他所有收到这个报文的人都无法解密，因只有B才有自己的私钥。

    5. B要给A发送信息时，亦同理加密。

    虽然非对称加密看上去非常完美，但依旧存在两个问题：

    1. 服务器将其公钥告诉客户端时，如何保证该公钥不被篡改？客户端如何确定服务端的身份不是伪造的？
    2. 公钥加密安全性高，但也由于两端各自用私钥解密，导致算法复杂，加密计算量大，如何提升效率？
    3.3.4.证书颁发机构

    CA是一个全球公认的、高度可信的第三方机构。它的核心职责是核实实体的身份，并为其签发数字证书，从而为互联网通信提供信任基石。

    • 公共CA：如Let's Encrypt, DigiCert, Comodo等。它们的根证书预装在操作系统和浏览器中，被全世界信任。用于HTTPS网站、公开API等。
    • 私有CA：它只在你自己的组织或应用范围内被信任，就像一个公司给自己员工发门禁卡。

    CA的作用是解决目标信任问题：

    1. 根证书： 每个CA都有自己的根证书（包含CA的公钥和私钥）。根证书是信任的起点，被预装在你的电脑、手机里。你信任这个CA，也就间接信任了它签发的所有证书。
    2. 签发过程： 当Google向CA申请证书时，CA会严格验证Google对域名 google.com的所有权。验证通过后，CA会用它的私钥 对Google的证书信息（包括域名、公钥等）进行数字签名，生成Google的证书。
    3. 验证过程： 当你的浏览器访问 https://google.com时：
    4. 服务器会出示它的证书。
    5. 浏览器用操作系统中预置的CA根证书的公钥，去验证服务器证书上CA的数字签名是否有效。
    6. 如果签名有效，说明这个证书是由一个可信的CA签发的，且内容在签发后未被篡改。
    7. 浏览器还会检查证书中的域名是否与正在访问的域名一致，以及证书是否在有效期内。
    3.3.5.证书

    证书是一个数字文件，遵循X.509标准。它本质上是将一个实体的身份信息与其公钥进行绑定，并由CA进行数字签名。

    字段 说明 类比身份证
    主题 证书持有者的信息，如通用名称，通常是域名或用户名。 姓名、身份证号
    颁发者 签发此证书的CA信息。 发证机关（某某公安局）
    有效期 证书的生效日期和过期日期。 有效期限
    公钥 最重要的信息之一，证书持有者的公钥。 （公开的）身份编码
    签名算法 CA用于签名的算法。 防伪技术类型
    数字签名 最重要的信息之二，CA用私钥对以上所有信息生成的哈希值。 公安局的官方印章/防伪码
    1. 身份绑定： 将公钥与一个特定的身份（如域名 www.example.com）强绑定。确保你拿到的公钥确实属于你正在通信的对象。
    2. 公钥分发： 提供一个安全、可信的途径来分发公钥。客户端可以从证书中安全地提取服务器的公钥。
    3. 建立信任： 作为SSL/TLS握手的信任起点。没有可信的证书，后续的所有加密通信都失去了安全基础。

    1. 客户端发送请求（Client Hello）：

    2. 支持的协议版本，如TLS1.0。

    3. 一个客户端生成的随机数，稍后用于生成会话密钥。
    4. 支持的加密套件，包括数据加密算法等，按客户端优先原则排序。

    5. 支持的压缩方法。

    6. 服务器回应（Server Hello）：

    7. 确认使用的加密通信协议版本，如TLS1.0。如果两端支持版本不一致，则服务器关闭加密通信。

    8. 一个服务器生成的随机数，稍后用于生成会话密钥。
    9. 确认加密套件。

    10. 服务器证书，装有服务器公钥。

    11. 客户端回应：

    客户端收到回应以后，首先验证服务器证书。如果证书不是可信机构颁布、或者证书中的域名与实际域名不一致、或者证书已经过期，就会向访问者显示一个警告，由其选择是否还要继续通信。如果证书没有问题，客户端就会从证书中取出服务器的公钥，然后向服务器发送下面三项信息。

    • 一个随机数pre-master-key，用服务器公钥加密，防止被窃听，稍后用户生成会话密钥。此时客户端已经拥有三个随机数，会计算出本次会话所用的会话密钥。
    • 编码改变通知，表示随后信息都将用双方商定的加密方法和密钥发送。

    • 客户端握手结束通知，表示客户端的握手阶段已经结束。这一项同时也是前面发送的所有内容的hash值，用来供服务器校验。

    • 服务器最后回应：

    服务器收到客户端的随机数pre-master key之后，计算生成本次会话所用的会话密钥。然后向客户端最后发送下面消息。

    • 编码改变通知，表示随后信息都将用双方商定的加密方法和密钥发送。
    • 服务器握手结束通知，表示服务器的握手阶段已经结束。这一项同时也是前面发送的所有内容的hash值，用来供客户端校验。

    至此，整个握手阶段全部结束，接下来客户端与服务器进入加密通信传输数据。

    通过一个随机数计算出来的会话密钥不够安全依旧有风险，所以用三次随机数共同计算出最后的会话密钥。

    在上述的过程中，证书与公私钥是为了生成传递会话密钥而生的，正常情况下后续的数据交互过程是不需要非对称加密算法参与的。

    4.Web资源与Web服务器

    4.1.Web资源

    Web资源可以分为静态资源和动态资源。

    • 静态资源：存放在Web服务器中的文件，可以是文本文件、HTML文件、图片文件或者视频文件。静态资源不需要经过应用的处理，直接就可以被用户访问。

    • 动态资源：需要经过服务器处理后提供给用户的资源。

    4.2.Web服务器

    Web服务器用来实现HTTP和相关TCP连接的处理，同时负责所提供资源的管理及服务相关的配置、控制及扩展模块的管理。
