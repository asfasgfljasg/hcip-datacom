    3.Nginx

    1.Nginx概述

    Nginx是一款轻量级、高性能的开源Web服务器和反向代理服务器，也可用作负载均衡器、HTTP缓存以及邮件代理服务器。

    1.1.Nginx运行架构

    • master进程：
    • 负责检查Nginx配置是否正确
    • 创建、监控worker进程的数量和状态
    • 接收对Nginx的管理指令，并作出对应操作
    • worker进程：
    • 处理客户端请求
    • 与后端服务器通信（如FastCGI、proxy等）
    • 接收master发来的指令，并完成对应操作
    1.1.1.Worker的抢占机制

    在高并发场景下，多个工作进程需要同时监听并处理同一端口的客户端请求。为了避免冲突 ，Nginx依赖操作系统的抢占机制来确保请求被合理分配。

    惊群效应

    由于Nginx的所有工作进程监听相同的端口，所以当客户端请求到达服务器时，Nginx的所有工作进程会被通知这一事件。默认情况下，每个进程都会尝试通过调用accept()函数来接收这个连接。此时，会导致惊群效应出现。所有工作进程同时被唤醒，竞争一个新的连接。导致CPU上下文切换增加、资源浪费。

    接受锁（方法1）

    为了避免惊群效应，Nginx使用一个互斥锁来控制对acceppt()函数的访问。在任何时候，这个锁只允许被一个Worker进程持有。

    1. 当一个新连接请求到达时，只有一个持有锁的Worker进程会被允许去执 accept()操作，接受这个新连接。
    2. 其他Worker进程因为没有拿到锁，会继续等待，不会被无效地唤醒。
    3. 当持有锁的Worker进程处理完 accept()后，会释放锁。
    4. 下一个Worker进程将有机会抢占到这个锁，为处理下一个连接请求做准备。

    锁是由Master进程进行分配的，当一个新的请求到达时，Master进程会感知到这个事件。主进程会根据内部的算法，决定将accept_mutex锁分配给空闲的Worker进程。只有拿到了这个锁的Worker进程，才有资格去执行accept()系统调用，正式接受这个新连接。

    Reuseport（方法2）

    reuseport是一个操作系统级别的选项，为每个进程创建独立的监听套接字和连接队列。这意味着多个Nginx Worker进程可以监听和接收来自客户端的连接，不需要争抢端口资源。

    当在Nginx配置中为监听指令加上reuseport参数后：

    1. 多个套接字，同一端口：Nginx的每个Worker进程会创建自己独立的监听套接字，并且所有这些套接字都绑定到完全相同的 IP 地址和端口（如 0.0.0.0:80）。这在没有reuseport的情况下是会报错“Address already in use”的，但reuseport选项允许这样做。

    2. 内核充当负载均衡器：当一个新的连接请求到达时，Linux内核现在成为了一个负载均衡器。它根据一种哈希算法（通常基于源IP、源端口、目标IP、目标端口）来决定将这个连接请求直接、均匀地分发到其中一个Worker进程的独立监听队列中。

    3. 无竞争唤醒：由于每个连接请求在到达时就已经被内核分配好了目标 Worker，因此只有一个对应的 Worker 进程会被唤醒。这个Worker进程可以毫无竞争地调用 accept()从自己的专属队列中取出连接。

    配置方法：

    server {
    listen 80 reuseport; # 关键就在这里！
    server_name example.com;
    ...
}
    1.1.2.异步I/O机制

    Nginx异步非阻塞I/O指的是：Nginx的工作进程永远不会因为等待而空闲，总是会去处理那些已经准备好的任务。

    当一个工作进程读取网络数据时，如果数据还没到达，阻塞模式会使进程“休眠”直到数据到来。Nginx的工作进程在尝试读取（read）或写入（write）数据时，如果遇到这种“暂时不可用”的情况，它绝不会等待，而是立刻放下这个连接，转头去处理其他已经“准备好”的连接。

    epoll：

    工作进程如何知道哪个连接“准备好了”呢？它不需要不停地去询问每个连接，而是依赖一个高效的“事件收集器”。

    • 在Linux上，这个收集器叫做 epoll。Nginx的工作进程会向 epoll注册它关心的所有连接及其事件（比如“当这个连接有数据可读时通知我”）。
    • 然后，工作进程会调用 epoll_wait()这个函数。此时，进程会进入休眠状态，不会消耗CPU。
    • 一旦任何一个被监视的连接准备好了（例如，客户端发来的请求数据已经到达内核缓冲区），epoll_wait()会立刻唤醒工作进程，并精确地告诉它：“连接A和连接C现在有数据可读了”。
    • 这种方式避免了循环检查所有连接的“轮询”开销，效率极高，可以轻松管理数万甚至数十万连接。
    1.1.3.事件驱动模型
    1. 任务调度核心：

    2. 操作系统会告诉Nginx：“现在有这些事可以做了”（例如，A 连接的数据已经从网络收到了，B 连接可以发送数据了）。Nginx的工作进程就是从这个“待办任务清单”中获取任务，然后高效处理。

    3. 灵活的任务分配：

    4. Nginx为不同类型的任务预设了不同的处理流程（回调函数）。

      • 新连接事件
      • 可读事件，请求数据已到达
      • 可写事件，发送数据缓冲区已清空

    5. reuseport：

    6. 没有 reuseport（传统模式）：门口来了一位新客人，餐厅里的所有领班（所有 Worker 进程）的寻呼机都会响。但只有一个领班能抢到为这位客人服务的资格，其他领班白跑一趟。这就是 “惊群效应”，会造成资源浪费。

      开启了 reuseport（现代模式）：操作系统（内核）充当了“大堂经理”。新客人来时，大堂经理会根据一种算法（如根据客人的来源地），直接指定一位领班去接待。这样，只有一个领班会被通知，其他领班完全不受打扰，可以继续处理自己手头的工作。这从根本上解决了“惊群效应”，是性能提升的关键。

    1.1.4.长连接

    长连接是Nginx高性能的关键场景之一，上述的异步非阻塞模型正是为高效处理海量长连接而生的。

    长连接的核心问题是：连接建立后，可能很长时间没有数据传输，但连接必须保持开放。如何用最少的资源管理这些“沉默”的连接？

    Nginx的解决方案非常优雅：

    1. 极低的内存占用

    • Nginx为每个连接只分配一个简单的连接结构体（ngx_connection_t），其内存开销非常小（通常在几百字节左右）。
    • 对比为每个连接创建一个线程（线程栈需要几MB）或进程（开销更大）的模型，Nginx可以用极小的内存代价维持数十万级别的长连接。

    2. 高效的事件监控

    • 对于空闲的长连接，Nginx工作进程只是在 epoll中注册一个“可读事件”的监听。
    • 随后，工作进程就在 epoll_wait()上休眠，完全不消耗CPU。
    • 只有当这个长连接上真的有数据到来，或者对端关闭连接时，epoll才会唤醒工作进程进行处理。这意味着，一万个空闲的长连接和一个空闲的长连接，对Nginx的CPU消耗几乎没有区别。

    3. 超时管理

    • 为了避免资源被永不关闭的坏连接耗尽，Nginx有完善的超时机制，通过计时器进行管理。重要的相关配置指令包括：
    • keepalive_timeout：设置长连接保持的时间。超过这个时间没有活动，Nginx会主动关闭连接。
    • proxy_read_timeout/ proxy_send_timeout：在与后端服务器建立的长连接上，设置读/写操作的超时时间。

    1.2.Nginx模块化体系

    Nginx本身是一个非常轻量级的核心，它只负责最基础的工作：事件驱动模型、进程管理、模块加载和配置文件解析。所有的高级功能，比如HTTP、负载均衡、邮件代理、安全控制等，都通过模块来实现。

    对于Nginx最重要的三个功能是：HTTP、反向代理和负载均衡。

    1.2.1.模块分类

    核心模块：这是Nginx正常工作的基础，无法被禁用。

    • ngx_core_module: 主模块，负责错误日志、进程优化、工作进程数等基础配置。
    • ngx_events_module: 事件模块，是配置事件模型（如 epoll, kqueue）的基础。
    • ngx_http_module: HTTP核心模块，定义了所有HTTP模块依赖的框架。
    • ngx_mail_module:Mail代理核心模块。
    • ngx_stream_module: 四层TCP/UDP代理核心模块。

    标准HTTP模块：

    • 处理类：
    • ngx_http_static_module: 处理静态文件请求（如 .html, .jpg）。
    • ngx_http_autoindex_module: 当URL以 /结尾时，生成目录列表。

    • ngx_http_index_module: 处理以 /结尾的请求，寻找 index.html等索引文件。

    • 反向代理类：

    • ngx_http_proxy_module: 提供反向代理功能，将请求转发到后端服务器。

    • ngx_http_upstream_module: 定义后端服务器组（Upstream），实现负载均衡。

    • 动态内容类：

    • ngx_http_fastcgi_module: 将请求转发给FastCGI进程（如PHP-FPM）。

    • ngx_http_uwsgi_module, ngx_http_scgi_module: 类似FastCGI，用于其他网关协议。

    • 控制与过滤类：

    • ngx_http_rewrite_module: 使用PCRE正则表达式重写URL。
    • ngx_http_access_module: 基于IP地址的访问控制（allow/deny）。
    • ngx_http_gzip_module: 启用Gzip压缩。
    • ngx_http_headers_module: 向响应中添加自定义头部。
    1.2.2.反向代理

    反向代理类似于公司电话总机，无论你需要联系哪个部门都需要先拨号到总计，再通过总机跳转到具体的分机。

    工作过程：

    1. 客户端浏览器输入URL经过DNS解析获取反向代理服务器的IP地址，随后向反向代理服务器发起HTTP请求。

    2. 反向代理服务器解析客户端发送的HTTP请求，根据该请求中的URL与自身的配置文件决定是否转发到后端服务器。

    3. Nginx与后端服务器建立一个新的、独立的TCP连接。

    4. Nginx重新构建并转发请求，新的请求中可能包含原始请求的Host、客户端真实IP、代理信息等。

    5. 若Nginx配置了缓存，会先检查是否有可用的缓存副本。如果没有或缓存过期才执行上一步。

    6. 后端服务器接收到请求后，根据配置生成HTTP响应返回给Nginx。

    7. Nginx会将后端服务器的响应放置到缓冲区，然后立刻关闭与后端服务器的连接，同时不紧不慢将响应给到客户端。（缓冲）这是为了提升性能不占用与后端服务器的连接。

    在整个通信过程中，客户端是感知不到后端服务器的。始终把反向代理服务器看作HTTP服务器。

    反向代理不仅仅是是中转站，它又很多的优势：

    • 隐藏后端服务器信息，提高安全性。
    • 缓存加速，反向代理服务器可以将后端服务器返回的静态内容缓存起来。后续有请求相同内容时就直接从缓存进行回复。
    • SSL终端/加密卸载：客户端与反向代理之间建立安全的 HTTPS 连接。反向代理负责SSL证书的验证和解密。然后，它以普通的 HTTP 协议（或新的HTTPS）与后端服务器通信。将消耗CPU资源的SSL加解密任务从应用服务器上卸载到专门的反向代理服务器上，让应用服务器能更专注于业务逻辑。
    1.2.3.负载均衡

    聪明的你现在肯定能感觉到，反向代理貌似更大的功能是保护了后端服务器，在提升性能方面并没有特别大的一个改善。那现在我们就可以使用反向代理的扩展——负载均衡。

    负载均衡指的是后端服务器的数量不再是一台，而是根据需要或预算部署多台具有处理能力的服务器。当一个请求进入Nginx后，Nginx根据配置的负载均衡算法，合理的将请求分布到后端服务器上。实现流量分担的作用，可以在很大程度上提升后端服务器接收与处理请求的能力。

    1.2.4.扩展

    此时，负载均衡器它依旧可能出现单点故障以及流量瓶颈的问题。我们可以通过DNS轮询的方式进行解决。

    1. 当客户端查询 example.com时，DNS服务器不会只返回一个IP，而是返回一个IP列表（例如 [IP_of_LB1, IP_of_LB2, IP_of_LB3]）。
    2. 通常，DNS服务器会采用轮询策略，每次改变返回IP的顺序（如第一次返回 [LB1, LB2, LB3]，第二次返回 [LB2, LB3, LB1]）。
    3. 客户端的DNS解析器通常会使用它收到的列表中的第一个IP地址。这样，不同的客户端就会连接到不同的负载均衡器上，流量从而被分摊。
    1.2.5.正向代理

    正向代理和反向代理有明显的不同点。反向代理实际上是为服务端提供服务的，而正向代理是为客户端提供服务的。

    客户端主动指定代理服务器，代理服务器根据客户端请求，动态解析目标地址。代理服务器隐藏了客户端的真实IP，目标服务器只能看到代理服务器的IP。

    工作过程：

    1. 客户端将请求发往代理服务器。
    2. 代理服务器转发请求到达目标服务器。
    3. 目标服务器返回响应给代理服务器。
    4. 代理服务器将响应返回给客户端。

    看似好像和反向代理相同，但是反向代理它再转发的时候是根据配置文件中预设的后端服务器地址进行转发。而正向代理是动态的根据客户端发送的请求中Host和URI字段进行转发的。

    所以，正向代理是主动的，反向代理是被动的。正向代理为客户端服务，目标动态决定。反向代理为服务器服务，目标预先固定的。

    • user nginx;：定义运行Nginx工作进程的用户

    HTTP块包含所有Server块，用于影响所有虚拟主机，每个Nginx实例只有一个HTTP块。HTTP模块定义HTTP协如何工作，提供Server块运行的基础环境。

    Nginx配置结构：
┌─────────────────────────────────────────┐
│            HTTP块（协议层）              │ ← 定义HTTP协议相关配置
├─────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐       │
│  │ Server块1    │  │ Server块2    │ ...  │ ← 定义具体网站服务

│  └─────────────┘  └─────────────┘       │
└─────────────────────────────────────────┘

    http {...}：HTTP的相关配置部分，包含了如日志格式、访问日志、文件传输选项、默认类型等各种与HTTP服务相关的具体设置，以及服务器的监听端口、名称、根目录和错误页面等配置。

    • log_format：定义了名为main的日志模板。
    • $remote_addr：客户端IP地址。
    • $remote_user：认证用户名。
    • $time_local：访问时间戳。
    • $request：完整HTTP请求头，如GET /index.html HTTP/1.1。
    • $status：HTTP状态码。
    • $body_bytes_sent：发送给客户端响应的字节数。
    • $http_referer：来源页面URL。
    • $http_user_agent：客户端使用的浏览器信息，如Mozilla/5.0 (Windows NT 10.0)。

    • $http_x_forwarded_for：经过代理时的真实客户端IP。

    • access_log：定于访问日志文件的存储路径与日志模板。

    • sendfile on：零拷贝文件传输，文件数据直接从内核空间发送到网络套接字，绕过用户空间，减少内存拷贝，提高文件传输性能。适用于静态资源。

    • tcp_nopush on：需要开启sendfile才能生效，在数据包填满后再发送，减少小包数量。

    • tcp_nodelay on：立即发送小数据包，减少延迟，与tcp_nopush优化不同场景，不冲突。

    • keepalive_timeout：持久连接的保持事件。

    • types_hash_max_size：设置MIME类型哈希表的最大大小，影响Content-Type响应头的查找性能，增大可处理更多MIME类型。
    • include /etc/nginx/mime.types;：引入/etc/nginx/mime.types 文件，用于定义不同文件类型的处理方式。
    • default_type application/octet-stream;：设置默认的MIME文件类型为 application/octet-stream 。当无法确定文件类型时使用的默认MIME类型，该类型表示二进制流文件。遇到这类文件浏览器默认进行下载。

┌─────────────────────────────────────────┐
│            HTTP块（协议层）              │ ← 定义HTTP协议相关配置
├─────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐       │

    • listen：该Server块的监听端口，默认IPv6和IPv4都监听了80。

    • server_name：主机名，_表示匹配所有未明确指定的域名。

    • root：定义网站根目录路径。

    • include：引入/etc/nginx/default.d目录下所有以.conf结尾的配置，可以在此目录下自定义配置。可能包含PHP、重写规则等。

    • error_page：错误页面配置，根据不同的状态码返回页面。

    2.4.数据压缩

    Nginx同样支持数据压缩功能，可有效减少网络传输的数据量，提高数据传输的效率和速度。

    默认情况下，Nginx没有开启压缩功能。另外，开启了gzip功能后，需要指定触发压缩的文件类型，否则无法生效。

    2.4.1.配置参数

    • gzip on;：启用gzip压缩功能

    • gzip_comp_level：设置压缩级别，取值1-9之间，数字越大压缩程度越高，但也会消耗更多的CPU资源

    • gzip_types：指定压缩的文件类型，可在/etc/nginx/mime.types中查找文件类型
    • gzip_buffers：设置用于压缩的缓冲区大小
    • gzip_min_length：指定出发压缩的最小响应体长度（数据大小）。默认情况下，如果相应体的长度小于20个字节，Nginx不会对其进行压缩。
    • 例如：如果设置了gzip_min_length 1000;，那么只有当响应体的长度大于或等于1000个字节时，Nginx才会对其进行压缩。

    2.5.keep-alive

    Nginx中的keep-alive默认已经开启，且在http模块中定义了超时时间为65s。

    2.5.1.配置位置

    Nginx中的keep-alive可以在多个模块中配置，且可以同时配置：

    配置位置 指令 作用范围 配置示例
    HTTP层 keepalive_timeout 全局所有连接 keepalive_timeout 65;
    HTTP层 keepalive_requests 全局所有连接 keepalive_requests 100;
    Upstream层 keepalive 后端连接池 keepalive 32;
    Server层 keepalive_timeout 当前虚拟主机 keepalive_timeout 30;
    Location层 keepalive_timeout 特定路径 keepalive_timeout 10;

    下级模块可覆盖上级模块中keep-alive的配置。

    2.5.2.配置参数

    keepalive_timeout：

    # 格式：keepalive_timeout [超时时间] [头部超时时间?];
keepalive_timeout 65;           # 连接保持65秒
keepalive_timeout 65 60;        # 65秒超时，Keep-Alive头显示60秒

    keepalive_requests：

    # 一个TCP连接上最多处理的HTTP请求数量
keepalive_requests 100;         # 处理100个请求后关闭连接

    Upstream的keepalive：

    upstream backend {
    keepalive 32;  # 每个worker进程保持32个空闲连接到后端
}
    2.5.3.配置示例
    server {
    keepalive_timeout 15;      # 15秒超时
    keepalive_requests 1000;   # 允许更多请求
}
    2.5.4.关闭keep-alive

    Nginx中关闭keep-alive的方式是将keepalive-timeout这是为0，但得保证每个模块都已经设置为0：

    http {
    keepalive_timeout   0;
}

    2.6.Location

    location是Nginx中的块级指令，其功能是用来匹配不同的URL请求，针对其做不同的处理和响应。

    location有两种匹配规则：

    1. URL类型匹配（四种参数，五种匹配方式）

    2. location [ = | ~ | ~* | ^~ ] uri { ... }

    3. location命名方式，用@标识

    4. location @name { ... }
    2.6.1.匹配类型

    针对URL总共有五种匹配方式，不同的匹配方式根据优先级有匹配顺序：

    • 其中，前缀优先匹配和前缀匹配在写法上是一样的，只是优先级有区别而已。

    • 匹配顺序：

    = > ^~ > ~ > ~ > ~* > 前缀匹配 > /
    匹配类型 语法 优先级 示例
    精确匹配 location = /path 最高 location = /login
    前缀优先匹配 location ^~ /path/ 高 location ^~ /static/
    正则匹配 location ~ pattern 中 location ~ \.php$
    正则匹配(不区分大小写) location ~* pattern 中 location ~* \.jpg$
    普通前缀匹配 location /path/ 低 location /api/

    精确匹配：

    精确匹配=指的是，用户访问的URI必须与表达式完全一致才能匹配成功。

    location = /abc/ {
  .....
 }

# 只匹配http://abc.com/abc
#http://abc.com/abc [匹配成功]
#http://abc.com/abc/index [匹配失败]

    正则匹配，区分大小写：

    location ~ \.php$ {
    fastcgi_pass 127.0.0.1:9000;
    include fastcgi_params;
}

    正则匹配，忽略大小写：

    location ~* \.(jpg|jpeg|png|gif|css|js)$ {
    expires 30d;
    access_log off;
}

    前缀优先匹配：

    location ^~ /index/ {
  .....
}
#以 /index/ 开头的请求，都会匹配上
#http://abc.com/index/index.page  [匹配成功]
#http://abc.com/error/error.page [匹配失败]

    前缀匹配：

    • 前缀匹配中有一个规则——最长匹配
    location /index/ {
  ......
}
location /index/test/ {
  ......
}
#http://abc.com/index  [匹配成功]
#http://abc.com/index/index.page  [匹配成功]
#http://abc.com/test/index  [匹配失败]
#http://abc.com/Index  [匹配失败]
# 匹配到所有uri
/index/test/gugujun

    内部跳转：

    location /index/ {
  error_page 404 @index_error;
}
location @index_error {
  .....
}
#以 /index/ 开头的请求，如果链接的状态为 404。则会匹配到 @index_error 这条规则上
    2.6.2.root与alias

    root和alias都属于location内部的指令（动作），用于指明响应客户端的文件路径。

    root

    root指令的工作原理是：将location匹配的完整URI拼接到root指定的路径后面，形成完整的文件路径。且URI会被完整保留。

    server {
    listen 80;
    server_name example.com;

    # 配置1：使用 root
    location /static/ {
        root /var/www/html;
    }
}

    当用户访问：http://example.com/static/css/style.css时，Nginx的寻找文件路径为root + URI = /var/www/html + /static/css/style.css。

    需要注意的是root指令会完整保留URI，所以/static/这部分会被完整保留下来。

    alias

    alias指令的工作原理是：用alias指定的路径直接替代掉location匹配到的部分，然后用URI的剩余部分拼接到替换后的路径后面。

    alias是替换，location的URI匹配到的部分会被丢弃。

    server {
    listen 80;
    server_name example.com;

    # 配置2：使用 alias
    location /static/ { # 匹配部分
        alias /var/www/html/;
    }
}

    当用户访问http://example.com/static/css/style.css

    • URI：/static/css/style.css
    • location匹配部分：/static/
    • URL剩余部分：css/style.css
    • 结果：alias路径 + URL剩余部分。var/www/html/css/style.css

    注意：

    alias后的路径必须是有斜杠的。例如：

    location /edu/ {
    alias /usr/share/nginx/html/edu_dir/;
}

    若有斜杠，则代表/usr/share/nginx/html/edu_dir/index.html

    若没有斜杠，则代表/usr/share/nginx/html/edu_dirindex.html

    为什么root没影响呢？

    同样的例子，对于root如果有/则：/usr/share/nginx/html/edu_dir//edu/index.html，如果没有/则：/usr/share/nginx/html/edu_dir/edu/index.html。

    之前我们演示的方式都是绝对路径方式，alias和root还可以用相对路径的方式指定路径。

    root

    注意：网站根目录是/usr/share/nginx/html当你使用相对路径时，会自动舍弃掉最后一个目录。

    2.6.4.location URI

    在location后的URI要斜杠和无斜杠是有很大区别的。

    • 以 /结尾的URI（如 /edu/）：表示这是一个目录。服务器会尝试在这个目录下寻找默认文件（如 index.html）。
    • 不以 /结尾的URI（如 /edu）：表示这是一个文件。服务器会尝试直接寻找这个文件。如果在目录中没有查找到该文件会重定向到重名的目录，并返回该目录下的index.html内容。

        alias /usr/share/nginx/html/edu_dir/;

    2.6.5.return

    用于立即停止处理，并返回指定的HTTP状态码或重定向到指定URL。

    • 立即生效：执行后立即终止请求处理
    • 性能高：直接返回响应，不进行复杂的重写逻辑
    • 适合简单的重定向和状态返回
    return code [text];
return code URL;
return URL;

    状态码返回：

    location /denied {
        return 403 "Access Denied";
}
location /test {
        return 200;
}

    重定向跳转：

    # 临时重定向 (302)
location /temp {
    return 302 https://www.baidu.com;
}

# 永久重定向 (301)
location /permanent {
    return 301 https://www.baidu.com;
}

# 简写形式（默认为302）
location /short {
    return https://www.baidu.com;
}
    2.6.6.rewrite

    基本语法：

    rewrite regex replacement [flag];
    • flag：
    • last：停止当前重写，用新URI重新匹配location
    • break：停止重写，继续处理当前location
    • redirect：临时重定向（302）
    • permanent：永久重定向（301）

    基本URL重写示例：

    # 将 /old/path 重写到 /new/path（内部重写，浏览器地址不变）
location /old {
    rewrite ^/old/(.*) /new/$1 last;
}

    2.9虚拟主机

    虚拟主机可以在一台服务器上运行多个网站，高效且成本低廉。之前学习的所有内容都可以在虚拟主机中配置。拥有了虚拟主机后，等于同时拥有了多台Web服务器。

    虚拟主机的分类：

    • 基于域名：这是最常见的类型，通过不同地域名来区分不同网站，服务器根据客户端请求中的域名来决定提供相应的网站内容。
    • 基于IP：服务器为每个虚拟主机绑定不同的IP地址，通过请求的IP地址来确定要提供的服务。这种方式需要服务器拥有多个IP地址。
    • 基于端口：通过不同的端口来区分不同的虚拟主机。用户在访问时需要在URL中指定端口号。

    Web服务器是通过客户端请求中携带的Host头判断访问的是哪台虚拟主机，随后加载虚拟主机配置将对应内容给到客户端。

    在nginx中虚拟主机使用server配置块进行配置，其配置文件放置在/etc/nginx/conf.d目录下。

    3.Nginx热升级

    Nginx热升级可以在Nginx的工作状态下，对当前Nginx版本进行升级或添加模块，并且不影响用户的访问。

    3.1.原理

    3.1.1.热升级的过程

    Nginx启动后，会有一个主进程（master process）和若干个工作进程（worker process）。主进程主要负责管理工作进程，接收信号，读取和更新配置等。工作进程负责处理实际的客户端请求。我们所需要做的就是把新的二进制包启动的worker进程，代替旧的二进制包启动的worker进程，即新二进制包替代旧二进制包。

    3.1.2.信号管理

    Nginx可以通过接收不同的信号来执行各种操作。Nginx是一个多进程应用，一般多进程通信可以采用共享内存、信号等通信方式。nginx的主进程和worker进程之间使用信号通信。开发者也会通过主动发送信号，控制nginx的行为，比如上面的热部署。

    通常我们不直接给worker进程发送信号，而是给master进程发送信号，希望通过master进程管理worker进程（master进程和worker进程之间也会互发信号进行通信）。

    3.1.3.常见信号
    1. TERM 或 INT ：快速终止 Nginx 进程。
    2. QUIT ：优雅地关闭 Nginx 进程。
    3. HUP ：重新加载配置文件，使配置生效，同时会重新打开日志文件。
    4. USR1 ：重新打开日志文件。
    5. USR2 ：启动新的主进程，进行热升级操作。
    6. WINCH ：逐步优雅地关闭工作进程（在热升级中使用）。

    通常使用kill命令向Nginx进程发送信号，如下：

    kill -HUP <nginx 主进程的 PID>
或
kill -SIGHUP <nginx 主进程的 PID>
    3.1.4.热升级信号交互流程
    1. 发送 USR2 信号给主进程：主进程会启动一个新的主进程，新主进程使用新的二进制文件。此时，旧主进程和新主进程会同时运行。
    2. 发送 WINCH 信号给旧主进程：旧主进程会逐步优雅地停止旧的工作进程。
    3. 新主进程启动新的工作进程：新工作进程使用新的二进制文件来处理请求。
    4. 发送 QUIT 信号给旧主进程：完全停止旧主进程，完成升级。

    整个过程中，通过逐步切换工作进程，实现了服务的不间断，从而达到热升级的目的。

    3.2.实操

    3.2.1.热升级流程
    1. 通过编译获取新的Nginx二进制文件
    2. 备份当前版本Nginx文件
    3. 将当前版本的Nginx文件替换为新版本文件
    4. 向当前版本master进程发送USR2信号
    5. 启用新版本的master进程
    6. 测试新版本Nginx工作是否正常
    7. 退出老版本Nginx进程

    Nginx热升级的前提是旧版Nginx需要通过编译安装，不能是二进制安装。热升级大致会分为两步，按照要求编译新的Nginx二进制文件；通过信号，完成新老进程的平滑过渡。

    3.2.2.编译安装旧版本Nginx
    1. 下载版本较低的Nginx：
    [root@qyt-gujun ~]# cd /opt/

[root@qyt-gujun opt]# wget https://nginx.org/download/nginx-1.22.1.tar.gz
    1. 编译安装Nginx：
    [root@qyt-gujun opt]# tar -zxvf nginx-1.22.1.tar.gz # 解压

[root@qyt-gujun opt]# cd nginx-1.22.1/

[root@qyt-gujun nginx-1.22.1]# ./configure --prefix=/usr/local/nginx    # 报错原因没有安装c++

[root@qyt-gujun nginx-1.22.1]# yum install -y gcc   # 安装gcc编译器

[root@qyt-gujun nginx-1.22.1]# ./configure --prefix=/usr/local/nginx    # 报错原因没有安装pcre

[root@qyt-gujun nginx-1.22.1]# yum install pcre pcre-devel -y

[root@qyt-gujun nginx-1.22.1]# ./configure --prefix=/usr/local/nginx    # 报错原因没有安装zlib

[root@qyt-gujun nginx-1.22.1]# yum install zlib zlib-devel -y

[root@qyt-gujun nginx-1.22.1]# ./configure --prefix=/usr/local/nginx    # 安装成功，且会告知相关文件的安装路径
