    2.Apache

    1.Apache概述

    Apache HTTP Server是由Apache软件基金会开发和维护的，简称为apache。Apache软件基金会是一个由众多开发者和贡献者组成的开源社区，不是由单一的个人开发的。众多的开发者和志愿者通过贡献代码、修复漏洞、改进性能等方式共同推动了Apache HTTP Server的发展和演进。

    简单来说，Apache是一个基于HTTP/HTTPS协议的软件，监听来自客户端的请求，找到对应的网页文件并响应。

    Apache的核心特点是模块化设计，绝大多数功能（如SSL、URL重写、PHP解析、身份验证等）都通过可加载模块实现。

    1.1.进程模型

    在Apache中有三种进程模型，进程模型指的是系统如何创建、管理、调度和销毁进程的一套规则和机制。也就是Apache在面对请求时不同的工作方式。

    进程：一个正在运行的程序的实例。每个进程都有自己独立的内存空间。进程之间切换开销较大。

    线程：进程内的一个执行流。同一进程下的所有线程共享内存空间。线程之间切换开销比进程小得多。

    1.1.1.Prefork MPM（预派生模型）

    工作原理：

    1. 主进程（以 root 权限启动）预先创建（fork）一批子进程。
    2. 每个子进程都是单线程的，并且在它的整个生命周期内，一次只处理一个请求。
    3. 主进程不处理请求，只负责监控子进程的数量：
    4. 当请求增多，空闲进程不足时，主进程会创建新的子进程。
    5. 当请求减少，空闲进程过多时，主进程会终止一些空闲的子进程。
    6. 每个请求都由一个独立的、完整的进程来处理。

    优点：

    1. 稳定性高：进程之间隔离，当一个子进程崩溃不会影响其他进程工作。
    2. 兼容性好：支持线程不安全的模块，例如某些老旧的PHP模块。
    3. 易于调试：由于进程是独立的，定位和调试问题更简单。

    缺点：

    1. 每个请求都需要一个独立的进程资源开销大，不适合高并发或大流量场景。
    2. 对进程的创建和删除较频繁，消耗的CPU会比较多。

    应用场景：

    1. 依赖apache较老的模块。

    2. 低频安全访问场景，如网络设备的web管理系统。

    步骤五：调整工作进程数量

    [root@qyt-gujun ~]# vim /etc/httpd/conf.modules.d/00-mpm.conf
<IfModule mpm_prefork_module>
        StartServers              5
        MinSpareServers           5
        MaxSpareServers          10
        MaxRequestWorkers         150
        MaxConnectionsPerChild   0
</IfModule>
[root@qyt-gujun ~]# systemctl restart httpd
    • StartServers：Apache启动时立即创建的子进程数量。
    • MinSpareServers：系统中最小空闲进程数。如果空闲进程少于这个值，Apache会快速创建新的子进程。
    • MaxSpareServers：系统中最大空闲进程数。如果空闲进程多于这个值，Apache会清理掉多余的进程释放资源。
    • MaxRequestWorkers：Apache同时能处理的最大请求数。超过这个数的请求将被放入队列等待。重要

    • 实际上就代表apache可以创建的最大子进程数量。根据内存大小调整。

    • MaxConnectionsPerChild：每个子进程在处理完一定数量的请求后会自动消亡。设置为0表示永不消亡。

    调优示例：

    假设你有一台 2GB 内存的服务器，专门用于运行Apache，每个Apache进程大约占用 20MB 内存。那么最大进程数可以估算为：

    2048MB / 20MB ≈ 100

    可以这样配置：

    <IfModule mpm_prefork_module>
        StartServers                     5
        MinSpareServers           5
        MaxSpareServers          10
        MaxRequestWorkers         100
        MaxConnectionsPerChild   10000
</IfModule>
    1.1.3.Worker MPM（工作者模型）

    Worker MPM是一种混合（多进程-多线程）模型，旨在保持稳定性的同时，提高并发能力。

    工作原理：

    1. 主进程创建多个子进程（与Prefork类似）。

    2. 每个子进程内部会创建多个线程。

    3. 每个线程一次处理一个请求。

    这样一来，服务器就可以用较少的进程资源来服务大量的并发请求。

    特点：

    • 进程和线程是两种并发单位，进程负责隔离，线程负责高效的请求处理。
    • 线程比进程更轻量化，线程共享同一进程内的内存空间，因此在处理大量并发请求时内存消耗会更低。

    在高并发场景下创建进程，需要分配独立的、完整的内存空间，类似于造一栋房子，开销很大。但是创建线程类似于在大办公室里增加一个工位，开销小的多。在Linux上启动一个进程的开销可能是启动一个进程的10倍甚至更高。

    举个例子，把进程理解成厨房，把线程理解成厨师。现在需要服务一百名顾客，用Prefork的方式需要有一百间厨房，每间厨房分配一名厨师。而Worker模式有几间非常大的中央厨房，每间厨房多名厨师一起工作，当客户变多，只需要增加厨师，不需要再盖厨房了。

    适用场景：

    1. 高并发网站：例如社交媒体、电子商务平台等需要处理大量并发请求的应用。
    2. 内存有限的服务器：在内存有限的情况下，Worker模型比Prefork模型更加高效。
    1.1.4.长连接场景

    需要清楚的是在长连接的场景中不论是Prefork还是Worker模型都会出现资源占用的情况。

    Prefork：当一个进程处理完用户发送的请求后，发现其是一个Keep-alive，在Keep-alive时间到达之前，这个进程必须被占用，它只能够等待。一旦在这个连接里有了新的请求它需要立刻响应，如果没有任何响应那当超时时间到达后，他就可以去干别的工作。

    Worker：与Prefork基本一致，只不过当前Worker模型是用线程来处理请求的。其资源浪费要比Prefork少的多。

    修改配置文件

LoadModule mpm_worker_module modules/mod_mpm_worker.so
<IfModule mpm_worker_module>
    # 天花板参数
    ServerLimit          10  # 最大进程数： 250 / 25 = 10
    ThreadLimit          25  # 每个进程最大线程数
    ThreadsPerChild      25  # 每个进程固定线程数
    MaxRequestWorkers    250 # 总线程数 = 10 * 25 = 250

    MaxSpareThreads     150  # 最大空闲线程数

    1.1.6.event异步IO事件模型

    Event MPM将其工作单元分为三类：

    1. 监听线程：负责接受新的网络连接。通常只有一个或极少数监听线程，因为她非常高效，一个线程就能轻松管理数万个连接。
    2. 工作线程池：真正干活的线程。当监听线程发现某个连接上有数据可读（如HTTP请求头），它会从池中分配一个空闲的工作线程来处理请求。工作线程基本上全部的时间都在处理实际的计算和I/O操作，永远不会因为等待网络而阻塞。
    3. 连接对象：代表了每个独立的HTTP连接。它们由监听线程管理，并被分配给工作线程。

    长连接处理：

    由于有监听线程的参与，所有的连接和请求都是给到监听线程，然后由监听线程判断并分配给具体的工作线程。工作线程百分百专注于工作，当它被监听线程分配一个任务后，它会立刻进行处理，处理完毕后立即释放，连接交还给监听线程。而这个工作线程会被分配到其他工作任务，不会去等待长连接。

    等于说将任务分层了，原本一个工作线程即要处理请求，又要监听。

    1.1.7.调整event模型

    要求Linux内核必须在2.6以上，支持epoll事件。

    <IfModule mpm_event_module>
    # --- 定义“天花板” ---
    ServerLimit              10      # 最大进程数（硬上限）
    ThreadsPerChild         25      # 每个进程的工作线程数
    MaxRequestWorkers      250      # 最大并发请求数 = ServerLimit * ThreadsPerChild

    # --- 定义异步连接处理 ---
    AsyncRequestWorkerFactor 2      # 【Event特有】计算初始异步监听线程数 (通常= CPU核心数 * 此因子)
    ListenBacklog          511      # 等待Accept的连接队列长度

    # --- 进程/线程池的动态调整 ---
    StartServers            3       # 启动时创建的进程数
    MinSpareThreads        75       # 最小空闲工作线程数
    MaxSpareThreads       250       # 最大空闲工作线程数

    # --- 进程生命周期管理 ---
    MaxConnectionsPerChild  10000   # 每个进程处理多少请求后重启（防内存泄漏）
</IfModule>

    2.1.5.实验二：文件类型

    在apache中文件类型的作用是告知浏览器“发送给你的文件是哪一种文件类型”，默认情况下由浏览器自己决定最终如何处理该类型的文件。apache的主配置文件及/etc/mime.types文件中定义了文件类型。

    例如，在主配置文件中增加如下字段，使客户端在访问*.pdf时进行下载：

    [root@Server ~]# cat /etc/httpd/conf/httpd.conf | grep pdf | grep -v '^#'
<IfModule mime_module>
    AddType application/x-pdf .pdf
</IfModule>
[root@http-server ~]# echo "this is pdf" > /var/www/html/1.pdf
[root@http-server ~]# systemctl restart httpd

    注意：

    • 当服务端可以识别到该文件的类型时，会将其携带在响应标头的Content-Type字段告知浏览器。

    • 若服务端在主配置文件和mime.types文件中没有识别到该文件的类型，则响应标头中无Content-Type字段
    • 在没有Content-Type的情况下，如何处理该文件由浏览器决定，若该文件字段较小浏览器会以“文本”的形式在线预览该文件。

    我们可以修改mime.types文件使特定后缀也被识别为mp4或pdf等。

    [root@Server ~]# cat /etc/mime.types | grep video/mp4 | grep -v '^#'
video/mp4                                       111
[root@http-server ~]# echo "111" > /var/www/html/1.111
[root@http-server ~]# systemctl restart httpd

    从上图中可以得知，浏览器是通过Content-Disposition来判断对一个文件是“下载”还是“在线预览”。当服务器发送的响应标头中没有Content-Disposition字段时才会根据文件类型判断执行动作。

    以*.mp4为例，mime.types文件中默认已经识别了mp4类型，所以发送给浏览器的响应标头中表明了类型，浏览器默认会以预览的形式执行。

    [root@http-server ~]# echo "mp4" > /var/www/html/good.mp4


    [root@http-server ~]# vim /etc/httpd/conf/httpd.conf

    Header set Content-Disposition "attachment" # 强制下载
</FilesMatch>
[root@http-server ~]# systemctl restart httpd

    2.3.访问策略

    apache中根据版本有两种访问策略设置类型：

    1. 旧时代（Apache 2.2）：使用 Order，Allow，Deny（来自 mod_access_compat模块）
    2. 新时代（Apache 2.4+）：使用 Require（来自 mod_authz_core和 mod_authz_host模块）
    2.3.1.Require方式介绍

    Require指令更直观、强大，是当前的标准做法。它必须包含在 <RequireAll>, <RequireAny>, 或 <RequireNone>等指令块中（不过对于简单的单条规则，Apache 会隐式理解为 <RequireAll>）。

    基本语法：

    <Directory "/var/www/html">
    # 允许所有访问
    Require all granted
</Directory>

<Directory "/var/www/html">
    # 拒绝所有访问
    Require all denied
</Directory>
    2.3.2.逻辑判断：

    当写两条或两条以上Require字段时，就必须使用逻辑判断语句。当只有一条RequireAll语句时默认使用RequireAll。

    • <RequireAll> = AND 逻辑（与）→ 所有条件都必须满足
    <Directory "/var/www/secure">
    <RequireAll>
        Require ip 192.168.1.0/24      # 条件1：IP必须在192.168.1.0/24网段
        Require user admin             # 条件2：必须通过用户认证且用户名为admin
    </RequireAll>
</Directory>
    • <RequireAny> = OR 逻辑（或）→ 任意一个条件满足即可
    <Directory "/var/www/site">
    <RequireAny>
        Require ip 192.168.1.100      # 条件1：来自IP 192.168.1.100
        Require ip 10.0.0.50          # 条件2：来自IP 10.0.0.50
        Require user guest            # 条件3：用户名为guest
    </RequireAny>
</Directory>

    • <RequireNone> = NOR 逻辑（或非）→ 所有条件都不满足

    • 访问结果：用户必须既不满足条件1也不满足条件2才能访问。

    <Directory "/var/www/safe">
    <RequireNone>
        Require ip 192.168.1.50       # 条件1：不能来自192.168.1.50
        Require ip 203.0.113.100      # 条件2：不能来自203.0.113.100
    </RequireNone>
</Directory>
    2.3.3.复杂示例：
    <Directory "/var/www/complex">
    <RequireAll>
        # 必须满足：基础网络条件 AND (用户认证条件 OR 特殊IP条件)

        # 基础网络条件：来自内网
        Require ip 192.168.0.0/16

        <RequireAny>
            # 用户认证条件：是管理员或审计员
            <RequireAll>
                Require valid-user
                Require user admin auditor
            </RequireAll>

            # 特殊IP条件：来自管理网段
            Require ip 10.1.1.0/24
        </RequireAny>
    </RequireAll>
</Directory>
    2.3.4.基于客户端IP地址：

    • 黑名单：允许所有IP访问，同时拒绝一个或多个IP。

    • 需要使用<RequireALL>进行包裹

    <Directory "/var/www/html">

    2.4.数据压缩

    apache的数据压缩功能通过mod_deflate模块实现，可以显著减小传输文件的大小，提高网站加载速度。

    # 查看已加载模块
httpd -M | grep deflate
或
[root@http-server ~]# cat /etc/httpd/conf.modules.d/00-base.conf | grep deflate
LoadModule deflate_module modules/mod_deflate.so

    即使激活了mod_deflate模块，apache也不会自动压缩任何文件类型，需要通过配置明确指定要压缩的MIME类型。

    2.4.1.工作过程

    当客户端向Apache服务器发送请求获取资源时：

    1. 浏览器发送的请求头上会添加Accept-Encoding字段，告知对方自己支持的解压方式（默认为gzip）。

    1. 服务器收到请求后，根据自身配置判断是否对响应数据进行压缩。

    2. 如果配置中指定对当前响应的文件类型进行压缩，服务器会使用mod_deflate模块对数据进行压缩。

    3. 压缩过程中，服务器会按照设定的压缩级别（1-9）对数据进行压缩，以达到减少数据量的目的。压缩级别越高，压缩效果越好，但是服务器CPU开销也越大。

    4. 压缩完成后，服务器在响应头中添加Content-Encoding字段，告知客户端传输的数据经过什么协议压缩。

    5. 客户端收到响应后，根据Content-Encoding信息得知压缩算法，根据算法进行解压缩。

    6. 解压缩后客户端可以正常显示或处理获取到的内容。

    2.4.2.参数
    SetOutputFilter DEFLATE # 启用全局数据压缩，针对所有文件压缩
DeflateCompressionLevel 1-9 # 设置数据压缩级别
AddOutputFilterByType DEFLATE # 定义对哪些类型的文件进行压缩

    基本配置：

    [root@http-server ~]# vim /etc/httpd/conf/httpd.conf
<IfModule mod_deflate.c>
    # 启用压缩
    SetOutputFilter DEFLATE     # 启用全局压缩，默认针对所有文件进行压缩
    DeflateCompressionLevel 6   # 压缩级别
    AddOutputFilterByType DEFLATE text/plain    # 在没有SetOutputFilter情况下，针对具体文件类型
</IfModule>
[root@http-server ~]# systemctl restart httpd
[root@http-server ~]# cp /etc/passwd /var/www/html/passwd   # 文件太小是不会触发压缩的


    [root@http-server ~]# curl -H "Accept-Encoding: gzip" 192.168.80.100/passwd -o /opt/test1

    2.5.日志

    在apache中主要有两种日志：

    • 访问日志：记录所有对服务器的请求。包括客户端IP、请求时间、请求的资源、状态码等。
    • 错误日志：记录服务器处理请求时出现的错误、警告等信息。对于调试问题至关重要。
    ErrorLog "logs/error_log"   # 指定错误日志的文件路径
LogLevel warn   # 日志级别
<IfModule log_config_module>    # 如果log_config_module模块被加载，则执行以下日志格式和记录配置
    LogFormat "%h %l %u %t \"%r\" %>s %b \"%{Referer}i\" \"%{User-Agent}i\"" combined
    LogFormat "%h %l %u %t \"%r\" %>s %b" common
    <IfModule logio_module>
      LogFormat "%h %l %u %t \"%r\" %>s %b \"%{Referer}i\" \"%{User-Agent}i\" %I %O" combinedio
    </IfModule>
    CustomLog "logs/access_log" combined
</IfModule>

    这一段是Apache默认的日志配置。

    基本语法：

    CustomLog “日志文件路径” 日志格式名称

    定义日志格式：LogFormat指令

    apache允许你自定义日志记录的内容。常见的预定格式有：

    • common：apache的通用标准格式。
    • combined：包含更多信息，是最常用的格式。

    常用日志格式符说明：

    • %h：客户端IP地址。
    • %l：由 identd决定的用户身份（通常为 -）。
    • %u：HTTP认证的用户名。
    • %t：请求时间。
    • %r：请求的第一行（包括方法、URI、协议）。
    • %>s：最终的状态码。
    • %b：返回给客户端的字节数（不含头信息）。
    • %{Referer}i：请求头中的 "Referer"（用户从哪个页面链接过来）。
    • %{User-Agent}i：客户端使用的浏览器（用户代理）。
    • %T：处理请求所花费的时间，以秒为单位。

    2.6.虚拟主机

    默认情况下，一台apache只能维护一个网站。例如我需要部署博客和论坛两个业务，那就必须拥有两台apache，那在成本上就会增加很多管理难度也会提高。

    虚拟主机可以在一台服务器上运行多个网站，高效且成本低廉。之前学习的所有内容都可以在虚拟主机中配置。拥有了虚拟主机后，等于同时拥有了多台Web服务器。

    虚拟主机的好处：

    • 资源隔离：不同的虚拟主机拥有独立的配置，包括服务器名称、网站根目录、访问控制规则等。
    • 节省成本：通过在一台服务器上配置多个虚拟主机，可以同时运行多个网站，无需为每个网站单独配置物理服务器，从而降低硬件成本和维护成本。
    • 灵活部署：可以轻松的添加、删除、修改虚拟主机的配置，快速适应业务的变化和扩展需求。

    • 优化性能：可以根据每个虚拟主机的流量和资源需求，进行有针对性地性能优化，如缓存设置、连接限制等。

    • 共享资源：多个虚拟主机可以共享服务器地硬件资源，如CPU、内存等。

    • 域名绑定：能够将不同的域名绑定到对应地虚拟主机上，使用户可以通过不同的域名访问不同地网站。

    虚拟主机的分类：

    • 基于域名：这是最常见的类型，通过不同地域名来区分不同网站，服务器根据客户端请求中的域名来决定提供相应的网站内容。
    • 基于IP：服务器为每个虚拟主机绑定不同的IP地址，通过请求的IP地址来确定要提供的服务。这种方式需要服务器拥有多个IP地址。
    • 基于端口：通过不同的端口来区分不同的虚拟主机。用户在访问时需要在URL中指定端口号。

    Web服务器是通过客户端请求中携带的Host头判断访问的是哪台虚拟主机，随后加载虚拟主机配置将对应内容给到客户端。

    2.7.1.1.整体流程：
    1. 创建证书颁发机构
    2. 为服务器生成证书签名请求
    3. 使用自建CA签署服务器证书

    2.7.1.2.实验步骤：
    1. 创建证书目录结构
    # 创建SSL目录结构
[root@HTTP-Server ~]# mkdir -p /etc/ssl/{ca,certs,private,csr}
[root@HTTP-Server ~]# mkdir -p /etc/ssl/ca/{newcerts,crl,private}

# 设置权限
[root@HTTP-Server ~]# chmod 700 /etc/ssl/private
[root@HTTP-Server ~]# chmod 700 /etc/ssl/ca/private

# 创建必要文件，该文件是openssl CA数据库文件，用于记录所有由该CA签发证书的详细信息
[root@HTTP-Server ~]# touch /etc/ssl/ca/index.txt
[root@HTTP-Server ~]# echo "01" | sudo tee /etc/ssl/ca/serial
01
    1. 创建OpenSSL配置文件
    tee /etc/ssl/openssl.cnf > /dev/null << 'EOF'
[ ca ]
default_ca = CA_default

[ CA_default ]
dir               = /etc/ssl/ca
certs             = $dir/certs
crl_dir           = $dir/crl
database          = $dir/index.txt
new_certs_dir     = $dir/newcerts
certificate       = $dir/ca.crt
serial            = $dir/serial
crl               = $dir/crl.pem
private_key       = $dir/private/ca.key
RANDFILE          = $dir/private/.rand

x509_extensions   = usr_cert
name_opt          = ca_default
cert_opt          = ca_default
default_days      = 375
default_crl_days  = 30
default_md        = sha256
preserve          = no
policy            = policy_match

[ policy_match ]
countryName             = match
stateOrProvinceName     = match
organizationName        = match
organizationalUnitName  = optional
commonName              = supplied
emailAddress            = optional

[ req ]
default_bits        = 2048
default_md          = sha256
default_keyfile     = privkey.pem
distinguished_name  = req_distinguished_name
attributes          = req_attributes
x509_extensions     = v3_ca
string_mask         = utf8only

[ req_distinguished_name ]
countryName                     = Country Name (2 letter code)
countryName_default             = CN
countryName_min                 = 2
countryName_max                 = 2

stateOrProvinceName             = State or Province Name (full name)
stateOrProvinceName_default     = Beijing

localityName                    = Locality Name (city, district)
localityName_default            = Beijing

0.organizationName              = Organization Name (company)
0.organizationName_default      = MyCompany

organizationalUnitName          = Organizational Unit Name (department)
organizationalUnitName_default  = IT Department

commonName                      = Common Name (FQDN or your name)
commonName_max                  = 64
commonName_default              = test1.openeuler.com

emailAddress                    = Email Address
emailAddress_max                = 64
emailAddress_default            = admin@mycompany.com

[ req_attributes ]
challengePassword               = A challenge password
challengePassword_min           = 4
challengePassword_max           = 20

[ usr_cert ]
basicConstraints = CA:FALSE
nsComment = "OpenSSL Generated Certificate"
subjectKeyIdentifier = hash
authorityKeyIdentifier = keyid,issuer

[ v3_ca ]
subjectKeyIdentifier = hash
authorityKeyIdentifier = keyid:always,issuer
basicConstraints = CA:true
keyUsage = cRLSign, keyCertSign

[ v3_req ]
basicConstraints = CA:FALSE
keyUsage = nonRepudiation, digitalSignature, keyEncipherment

[ server_cert ]
basicConstraints = CA:FALSE
nsCertType = server
nsComment = "OpenSSL Generated Server Certificate"
subjectKeyIdentifier = hash
authorityKeyIdentifier = keyid,issuer:always
keyUsage = digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
subjectAltName = @alt_names

[ alt_names ]
DNS.1 = test1.openeuler.com
DNS.2 = www.test1.openeuler.com
IP.1 = 127.0.0.1
EOF
    1. 生成CA
    # 生成CA私钥，4096代表密钥长度
openssl genrsa -out /etc/ssl/ca/private/ca.key 4096

# req证书请求，-new创建新证书请求，-days证书有效期，-key指定私钥，-out输出证书文件，-config指定配置文件，-subj设置证书主题信息，
openssl req -new -x509 -days 3650 -key /etc/ssl/ca/private/ca.key \
  -out /etc/ssl/ca/ca.crt -config /etc/ssl/openssl.cnf \
  -subj "/C=CN/ST=Beijing/L=Beijing/O=MyCompany/OU=IT Department/CN=MyCompany Root CA"

[root@HTTP-Server ~]# chmod 400 /etc/ssl/ca/private/ca.key
    字段 代码 含义 示例值
    C Country 国家代码 CN（中国）
    ST State/Province 省/州 Beijing（北京）
    L Locality 城市 Beijing（北京）
    O Organization 组织名称 MyCompany
    OU Organizational Unit 部门 IT Department
    CN Common Name 通用名称 MyCompany Root CA
    1. 生成服务器证书
    openssl genrsa -out /etc/ssl/private/apache.key 2048

openssl req -new -key /etc/ssl/private/apache.key \
  -out /etc/ssl/csr/apache.csr -config /etc/ssl/openssl.cnf \
  -subj "/C=CN/ST=Beijing/L=Beijing/O=MyCompany/OU=IT Department/CN=test1.openeuler.com"

# ca证书管理命令，-extensions使用配置文件中定义的服务器证书扩展，-notext无文本输出
openssl ca -config /etc/ssl/openssl.cnf -extensions server_cert \
  -days 730 -notext -md sha256 \
  -in /etc/ssl/csr/apache.csr -out /etc/ssl/certs/apache.crt

chmod 400 /etc/ssl/private/apache.key

chmod 444 /etc/ssl/certs/apache.crt
    1. 验证生成的证书
    openssl verify -CAfile /etc/ssl/ca/ca.crt /etc/ssl/certs/apache.crt

openssl x509 -in /etc/ssl/certs/apache.crt -text -noout

openssl rsa -in /etc/ssl/private/apache.key -check -noout
    1. 安装和配置Apache
    [root@HTTP-Server ~]# yum install httpd mod_ssl -y
    1. 配置Apache SSL虚拟主机

    3.PHP

    Apache默认只提供静态网页资源访问，无法提供动态应用程序的访问。通过fastcgi等方法可以使Apache支持动态应用程序。

    Apache可以通过多种方式运行PHP，主要区别在于PHP解释器的集成方式：

    mod_php模块（传统方法）：

    • PHP作为Apache的一个模块直接加载
    • 每个Apache进程都内置了PHP解释器，紧紧捆绑在一起无法分开
    • 处理PHP请求的工作落到了Apache工作线程身上
    • 适合传统的共享主机环境

    FastCGI模式（现代方式）：

    • PHP通过PHP-FPM(FastCGI Process Manager)独立运行
    • Apache通过mod_proxy_fcgi模块与PHP-FPM通信
    • 该场景中Apache和PHP解耦，运行环境更灵活

    3.1.什么是CGI？

    CGI通用网关接口，是一种标准的接口规范，用于Web服务器与外部程序之间的通信，以实现动态网页的生成。CGI的优点是简单易懂，易于实现。但它的缺点也很明显，每次请求都需要启动一个新的进程进行处理，这会带来较大的性能开销，特别是在高并发的情况下。

    CGI的处理流程：

    1. 客户端向Web服务器发送一个访问动态资源的请求。
    2. Web服务器收到请求后，确定该请求需要调用CGI程序进行处理。
    3. Web服务器启动一个新的进程来运行CGI程序，并将客户端请求相关信息通过环境变量和标准输入传递给CGI程序。
    4. CGI程序从环境变量和标准输入中获取所需的数据，传递给后端进程如PHP
    5. CGI程序根据处理结果生成动态的HTML或其他类型的输出，并将其通过标准输出返回给Web服务器。
    6. Web服务器获取CGI程序的输出，并将其作为响应发送回客户端的浏览器。
    7. 浏览器接收并显示服务器返回的响应内容。

    3.2.FastCGI

    FastCGI快速通用网关接口是一种通信协议和接口，用于在Web服务器和后端的应用程序之间进行高效的数据交换和处理。

    FastCGI致力于减少Web服务器与CGI程序之间互动的开销，从而使服务器可以同时处理更多的Web请求。与为每个请求创建一个新的进程不同，FastCGI使用持续的进程来处理一连串的请求。这些进程由FastCGI进程管理器管理，而不是Web服务器。

    FastCGI的处理流程：

    1. Web服务器启动时，会初始化FastCGI环境。
    2. 当客户端发送动态网页请求到Web服务器时，Web服务器根据配置确定需要使用FastCGI来处理该请求。
    3. Web服务器通过预先建立的网络连接（通常是TCP连接或Unix Domain Socket）将请求信息按照FastCGI 协议的格式发送给FastCGI进程。
    4. FastCGI进程接收到请求后，进行解析和处理。它从接收到的数据中获取请求的方法、路径、参数等信息。
    5. FastCGI进程根据请求执行相应的处理逻辑，可能包括与数据库交互、计算、生成动态内容等。
    6. 处理完成后，FastCGI进程将响应的状态码、头部信息和主体内容按照FastCGI协议的格式通过网络连接回传给Web服务器。
    7. Web 服务器接收到FastCGI进程的响应，并将其发送给客户端。

    3.3.套接字和端口方式的区别

    在使用PHP-FPM时可以选择通过Unix套接字或TCP端口进行通信。两者各有优缺点，选择哪种方式主要取决于性能需求和部署环境。

    3.4.PHP-FPM的本质

    PHP-FPM有三个身份：

    1. PHP进程管理器
    ps aux | grep php-fpm
root      1234  0.0  0.1 123456  7890 ?        Ss   10:00   0:00 php-fpm: master process (/etc/php/8.1/fpm/php-fpm.conf)
www-data  1235  0.0  0.5 234567 12345 ?        S    10:00   0:01 php-fpm: pool www
www-data  1236  0.0  0.5 234567 12345 ?        S    10:00   0:01 php-fpm: pool www
    • 主进程：管理所有Worker进程。

    • 工作进程：实际处理PHP请求的工作进程。

    • FastCGI协议实现：使得Web服务器能够与PHP进程通信。

    • PHP解释器载体：每个Worker进程都包含完整的PHP解释器。

    完整请求处理流程：

    客户端请求
    ↓
Apache/Nginx (Web服务器)
    ↓ 通过FastCGI协议通信
PHP-FPM (主进程 + Worker进程)
    ↓ Worker进程执行PHP代码
PHP解释器
    ↓
返回HTML响应

    3.6.使用PHP-FPM

    默认情况下使用的就是PHP-FPM，如果你想从mod_php模式修改为PHP-FPM，只需要修改一个字段：

    [root@qyt-gujun ~]# vim /etc/httpd/conf.d/php.conf
    <FilesMatch \.(php|phar)$>
        SetHandler "proxy:unix:/run/php-fpm/www.sock|fcgi://localhost"
        #SetHandler application/x-httpd-php
    </FilesMatch>

[root@qyt-gujun ~]# systemctl restart httpd
    • SetHandler 指令用于指定请求的处理方式。
    • proxy:unix:/run/php-fpm/www.sock 表示通过 Unix 套接字 /run/php-fpm/www.sock 与 PHP-FPM 进行通信。
    • fcgi://localhost 则是另一种指定与本地的 FastCGI 进程进行通信的方式。
    • 所以在我们安装完php-fpm后，默认情况下使用套接字与本地的FastCGI进行通信，把PHP的请求交给本地PHP进行处理。
