    04.HAProxy

    1.基础原理

    1.1.HAProxy是什么？

    HAProxy是一款提供高可用性、负载均衡以及基于TCP和HTTP应用的代理服务器，支持虚拟主机，它是免费、快速并且可靠的一种解决方案。

    其核心使命是将客户端的网络请求分发到后端多个服务器上，以实现高可用性、高并发处理能力和可扩展性。

    中文官方文档： HAProxy 文档

    核心作用：

    1. TCP代理：在客户端和服务器之间建立两个独立的连接，桥接流量。
    2. HTTP反向代理：接收HTTP请求，并以不同的连接将其转发给后端服务器。
    3. SSL/TLS终结器/发起器/卸载器：可以处理客户端的SSL加密，也可以明文或重新加密的方式与服务器通信。
    4. 协议规范器：对TCP和HTTP协议进行验证和修复，保证后端服务器免受畸形协议数据包的攻击。

    5. 流量调节器：可以实施速率限制，保护服务器免于过载。

    6. 缓存代理：可以在内存中缓存响应，但设计目标是节省HAProxy自身资源，而非替代专业缓存。

    1.2.工作原理

    1.2.1.传统模型

    在传统的模型中，当操作系统收到一个连接请求就需要占用一个专门的进程为他服务。当有其他连接进入操作系统时就需要创建其他进程一对一服务，会导致频繁删除或创建进程，浪费CPU资源。当一个进程执行accept()或read()时，它会调用一个阻塞式的系统调用。例如进程需要等待网络数据到达、或读取、写入时，内核会让进程进入睡眠状态，直到它等待的事件（处理完毕）发生，内核才会叫醒它们，效率较低。

    综上所述，效率低下的原因有两点：

    1. 阻塞式：进程不是时时刻刻都处于活跃状态，且会被单一连接占用。
    2. 模型：内核在这里扮演的角色是叫醒服务，功能单一。
    1.2.2.事件驱动模型与非阻塞I/O

    在事件驱动模型中：

    1. 统一监听：一个主进程负责监听所有连接（如网络端口）。

    2. 事件记录与等待：当没有事件发生时，进程并不主动轮询，而是休眠并将CPU资源让出。它依赖操作系统内核（通过epoll、kqueue等机制）来记录和通知哪些连接上有事件发生（如新连接到达、数据可读、可写）。

    3. 批量处理：当事件发生时（例如，一个网络数据包到达），操作系统会唤醒进程，并提供一个就绪事件列表。进程随后批量地、高效地处理这些已就绪的事件。

    4. 非阻塞处理：在处理每个事件时，进程使用非阻塞I/O进行操作。如果某个操作（如读取数据）不能立即完成，进程不会等待，而是立即处理列表中的下一个就绪事件。

    从0-1：

    1. 当前没有任何事件时，主进程休眠不占用任何cpu。
    2. 当有事件发生时（新连接），内核先将该事件记录下来并唤醒主进程告诉其当前要做的任务。
    3. 主进程被唤醒根据事件进行处理，调用内核执行read()、write()等，随后立即执行其他事件，永不等待。
    4. 当处理结果出来后，内核会告知主进程让它来接手。

    从1-2：

    1. 如果现在有非常多的任务，如读写未完成还有100个新连接等。
    2. 主进程依旧是先完成手头能干的事，内核帮助它把当前可以干的事一一记录，然后告诉主进程。
    3. 主进程按照顺序，一条一条处理。

    另外，在单进程模型中，只能使用一个CPU核心，负载非常高，只有当一个CPU核心被该进程百分百占满，才会引入多线程。所以，下面就研究单进程和多进程模型了。所以，多进程模型的目的是为了将负载分摊到多个CPU核心上，实现水平扩展。

    总结：

    • 事件驱动模型：私人秘书，帮你不断汇总所有要处理的事，主进程就乖乖按照它的列表一条条干。
    • 非阻塞：服务员帮你点完菜，会站在你边上等菜做完么？那肯定是有其他客人就服务其他客人，有盘子端就端盘子去了，没活干摸鱼去了呀！
    1.2.3.进程模型

    既然事件循环机制已经这么高效了，为什么还需要多进程/线程呢？

    • 和集群一样，单一情况下效率和性能再高也架不住量大。

    一个事件循环只能跑在一个CPU核心上。当负载非常高，单个CPU核心成为瓶颈时，就需要将负载分摊到多个核心上。在多进程/线程模型中，每个工作进程/线程都运行着自己独立的事件循环。这不再是“一个连接一个线程”的落后模式，而是 “一个CPU核心一个事件循环” 的高效模式。

    1.2.4.状态机

    从上文中我们已经得知，内核在事件驱动模型里是一个秘书的角色，它负责将任务汇总成表告知进程，指导主进程干活。那对于主进程来说，这张“表”是怎么指导它干活的呢？他怎么知道它要干什么、怎么干呢？——状态机

    HAProxy为不同协议（如纯TCP、HTTP）实现了不同的状态机。

    以HTTP GET请求为例：

    1. 状态：HTTP_MSG_RQBEFORE（请求开始前）

    2. 触发事件：事件循环通知：“客户端连接上有数据可读”。

    3. 处理动作：状态机被唤醒。它知道连接刚建立，应该等待HTTP请求行。它尝试从网络缓冲区中读取数据。

    4. 转换：如果读到了完整的请求行（如 GET /index.html HTTP/1.1\r\n），则状态转换到 HTTP_MSG_RQLINE（处理请求行）。

    5. 状态：HTTP_MSG_RQLINE（处理请求行）

    6. 处理动作：解析请求行（方法、URI、版本）。验证其合法性。

    7. 转换：如果解析成功，则状态转换到 HTTP_MSG_RQHDR（等待解析请求头）。

    8. 状态：HTTP_MSG_RQHDR（处理请求头）

    9. 处理动作：继续读取数据，一行一行地解析HTTP头部（如 Host:, User-Agent:），直到遇到一个空行 \r\n，表示头部结束。

    10. 转换：收到空行后，状态转换到 HTTP_MSG_RQBODY（等待请求体）。对于GET请求，没有请求体，所以可能立即转换到下一个状态。

    11. 状态：HTTP_MSG_RQBODY（处理请求体）

    12. 处理动作：对于GET请求，发现没有请求体（根据 Content-Length或 Transfer-Encoding判断）。

    13. 转换：状态转换到 HTTP_MSG_BACKEND_SELECT（开始选择后端服务器）。

    14. 状态：HTTP_MSG_BACKEND_SELECT（选择后端）

    15. 处理动作：这不是网络I/O状态，而是逻辑状态。HAProxy根据配置的规则（ACL、负载均衡算法）选择一个可用的后端服务器。

    16. 转换：选择完成后，状态转换到 HTTP_MSG_CONNECT（连接后端）。

    17. 状态：HTTP_MSG_CONNECT（连接后端）

    18. 处理动作：与选定的后端服务器建立TCP连接。

    19. 转换：连接建立成功后，状态转换到 HTTP_MSG_SEND_REQ（发送请求）。

    20. 状态：HTTP_MSG_SEND_REQ（发送请求）

    21. 处理动作：将完整的HTTP请求（它已缓存在自己的缓冲区中）发送给后端服务器。

    22. 转换：数据进入发送缓冲区后，状态转换到 HTTP_MSG_WAIT_RESP（等待响应）。

    23. 状态：HTTP_MSG_WAIT_RESP/ HTTP_MSG_RESPONSE（等待并处理响应）

    24. 这个过程类似于请求的处理，状态机会经历解析状态行、响应头、响应体等状态。

    25. 状态：HTTP_MSG_DONE（完成）

    26. 处理动作：记录日志，清理资源。
    27. 转换：如果连接是 Keep-Alive，状态机可能重置回初始状态，等待同一个连接上的下一个请求。否则，关闭连接。

    总结：

    所以，进程根据状态机机制会非常清楚的知道自己每一步需要干什么、怎么去操作。以及出现问题应该怎么去处理，保证它能够完美的处理事件。

    1.3.与Nginx对比

    HAProxy专为负载均衡而生，整个架构都围绕着如何在多个后端服务之间最高效、最可靠地分发流量。Nginx负载均衡对于它只是一个“副业”，本质上是Web服务器，负载均衡功能是其反向代理的延申，负载均衡的功能相对简单。

    1.3.1.功能比较

    • 负载均衡能力：

    • HAProxy：主要专注于负载均衡，支持第4层和第7层的流量调度。它的强项在于处理复杂的负载均衡策略，如基于源 IP、URL路径、Cookie等的流量分发。

    • NGINX：虽然NGINX也支持第4层和第7层负载均衡，但其负载均衡功能相对简单，更适合处理HTTP/HTTPS流量。

    • 性能表现：

    • HAProxy：在处理TCP流量时表现出色，特别是在高并发场景下。它的连接管理能力非常强大，能够有效减少延迟。

    • NGINX：在处理静态文件和缓存时性能出众，其事件驱动架构使其能够高效处理大规模的HTTP请求。

    • 扩展性：

    • HAProxy：虽然HAProxy的功能专注于负载均衡，但通过其配置文件，可以实现非常复杂的流量控制策略。

    • NGINX：由于其模块化设计，NGINX的扩展性非常强，用户可以通过第三方模块实现额外功能。

    • 健康检查：

    • HAProxy：提供了高级的健康检查机制，可以基于各种条件进行后端服务器的状态检测。

    • NGINX：健康检查功能较为基础，但通过第三方模块可以扩展其功能。

    1.3.2.使用场景比较
    • HAProxy适用场景：
    • 大规模Web应用程序的负载均衡，尤其是需要复杂的流量控制策略时。
    • 高性能TCP负载均衡，如数据库集群的流量分发。

    • 高可用性场景，如需要主备切换和会话保持的关键业务系统。

    • Nginx适用场景：

    • 需要多功能服务器的场景，如同时处理静态文件、代理流量、终止SSL、负载均衡等。
    • 高并发HTTP服务，如内容分发网络（CDN）、视频流媒体等。
    • 需要轻量级反向代理和缓存服务器的应用程序。

    总结：

    • 当你需要一个专业、可靠、需要精细控制和深度可视化的负载均衡软件时，可以选择HAProxy。
    • 当你需要一个功能全面的网关，希望它既能做负载均衡，又能高效处理静态文件、重写URL、运行Lua脚本等，可以选择Nginx。

    2.配置介绍

    2.1.配置文件基础结构

    一个典型的HAProxy配置文件包含以下五个主要部分，顺序是固定的：

    • global：全局配置，影响HAProxy进程本身的参数。
    • defaults：为后续的frontend/backend/listen设置默认参数。
    • frontend：定义如何接收客户端连接（前端）。
    • backend：定义将流量发送到哪些服务器（后端）。
    • listen：将frontend和backend合二为一的简化配置段。

    配置文件路径：/etc/haproxy/haproxy.cfg。

    2.1.1.global段

    用于配置与Linux系统、性能、安全相关的全局参数。

    global
    daemon                    # 以守护进程方式运行
    user haproxy              # 运行用户
    group haproxy             # 运行组
    maxconn 100000            # 每个进程的最大连接数
    stats socket /var/run/haproxy/admin.sock mode 660 level admin
                              # 启用管理套接字，用于动态管理
    ssl-default-bind-ciphers ECDHE-RSA-AES128-GCM-SHA256
                              # 全局SSL加密算法设置
    log 127.0.0.1 local2      # 定义日志输出

    管理套接字的作用：

    管理套接字是HAProxy的实时控制中心。它提供了一个UNIX套接字接口，允许你在不重启HAProxy进程的情况下，动态地查询状态、修改配置、进行故障排查。HAProxy的监控面板也是通过该功能实现的。

    • 实时服务器管理
    # 将服务器设置为维护模式
echo "disable server backend/web1" | socat stdio /var/run/haproxy/admin.sock

# 重新启用服务器
echo "enable server backend/web1" | socat stdio /var/run/haproxy/admin.sock

# 动态修改服务器权重
echo "set weight backend/web1 50" | socat stdio /var/run/haproxy/admin.sock
    • 实时统计和监控
    # 查看前端统计信息
echo "show info" | socat stdio /var/run/haproxy/admin.sock

# 查看后端服务器状态
echo "show stat" | socat stdio /var/run/haproxy/admin.sock

# 查看当前活动会话
echo "show sess" | socat stdio /var/run/haproxy/admin.sock

    日志：

    global
    log <ip:port> <facility> [level]

    127.0.0.1：日志的接收地址，将日志发送到本地主机的syslog守护进程。也可以配置为远程日志服务器IP，集中日志收集。

    local2：日志设施，syslog的分类表示，取值范围是0-7。不同的设施可以用来区分不同来源的日志，便于过滤和处理。

    • 在syslog中的对应配置：/etc/rsyslog.conf

    • # 将local2设施的日志写入单独文件 local2.* /var/log/haproxy.log

    2.1.2.defaults段

    定义frotend和backend的默认值，避免重复配置。后续的frontend/backend会自动继承这些参数，也可被覆盖。

    defaults
    mode                    http      # 工作模式：HTTP七层代理
    log                     global    # 使用全局日志设置
    option                  httplog   # 启用详细HTTP日志格式
    option                  dontlognull # 不记录空连接，减少日志噪音
    retries                 3         # 连接失败后重试3次
    timeout http-request    5s        # 等待完整HTTP请求的超时（防慢速攻击）
    timeout queue           1m        # 请求在队列中最长等待1分钟
    timeout connect         5s        # 连接后端服务器的超时
    timeout client          1m        # 客户端不活动超时
    timeout server          1m        # 服务器端不活动超时
    timeout http-keep-alive 5s        # Keep-Alive连接空闲超时
    timeout check           5s        # 健康检查超时
    maxconn                 3000      # 单个进程最大并发连接数
    default_backend web_servers       # 未匹配规则时的默认后端

    配置优先级：

    frontend/ backend/ listen> defaults> global

    • 最具体的配置段拥有最高优先级

    • 如果没有特殊说明，就继承上一级的设置

    mode设置：

    frontend/backend中的mode覆盖defaults

    defaults
    mode http        # 默认模式：HTTP

frontend web_fe
    bind *:80
    # 这个frontend继承defaults的mode http

backend api_be
    mode tcp         # 明确覆盖为TCP模式
    server s1 10.0.1.10:8080

backend web_be
    # 没有指定mode，继承defaults的mode http
    server s2 10.0.1.11:80

    前后端配合：

    1. 前后端统一TCP模式（四层负载均衡）

    2. 前后端统一HTTP模式（七层负载均衡）

    3. 不可以混合使用 。

    2.1.3.frontend段

    这是客户端连接的地方，定义监听地址、端口和入站流量规则。

    配置示例：

    frontend web_front
    bind *:80                 # 监听所有IP的80端口
    bind *:443 ssl crt /etc/ssl/site.pem
                              # 监听HTTPS，并指定证书，接收HTTPS请求并解密后续以明文方式向后端转发
    # 访问控制：拒绝无效Host头
    acl invalid_host hdr(host) -i # 检查HTTP请求头中的HOST字段是否为空，-i标识忽略大小写
    http-request deny if invalid_host   # 若匹配上invalid_host则拒绝该请求

    # 根据域名进行内容路由
    acl host_blog hdr(host) -i blog.example.com # 请求头host匹配，忽略大小写
    acl host_api hdr(host) -i api.example.com
    acl static path_beg /static /images  
                              # 匹配URL以/static或/images开头的路径

    use_backend blog_servers if host_blog   # 如果匹配上了，向指定后端服务器组转发
    use_backend api_servers if host_api
    use_backend static_servers if static
    default_backend         http_back
    # 都不匹配时，使用default_backend
    2.1.4.backend段

    用于定义一组真实服务器及其负载均衡策略。

    配置示例：

    backend web_servers
    balance roundrobin        # 负载均衡算法：轮询
    option httpchk GET /healthcheck
                              # 定义健康检查方式

    # 定义真实服务器
    server web1 192.168.1.10:80 check maxconn 100 weight 10
    server web2 192.168.1.11:80 check maxconn 100 weight 10
    server backup 192.168.1.12:80 check backup
                              # 备份服务器，平时不接收流量

backend static_servers
    balance source           # 基于源IP的哈希算法
    server static1 192.168.1.20:80 check

    • check：启用健康检查

    • maxconn：限制到该服务器的最大连接数

    • weight：权重，越高接收越多流量

    • backup：标记为备份服务器

    2.1.5.listen段

    将frontend和backend合并的简化配置，适用于简单场景。

    listen stats
    bind *:1936
    stats enable
    stats uri /haproxy?stats
    stats auth admin:password  # 认证信息

listen web_service
    bind *:80
    server web1 192.168.1.10:80 check
    server web2 192.168.1.11:80 check

    完整配置：

    listen stats
    # 绑定和模式
    bind *:8080
    mode http

    # 启用统计

    stats hide-version          # 隐藏版本号
    stats show-legends          # 显示图例
    stats show-node             # 显示节点名
    stats show-desc "Production LB"  # 显示描述

    # 访问控制
    stats uri /haproxy?stats    # 统计页面URI
    stats realm "HAProxy Statistics"  # 认证域
    stats auth admin:password123      # 基本认证
    stats refresh 5s            # 自动刷新间隔
    # 权限控制
    stats admin if TRUE         # 管理权限条件，允许在监控界面上执行管理操作，如禁用服务器。

    3.2.ACL

    在HAProxy中，ACL不是一份固定的列表，而是一条条件判断规则。它的核心作用是根据某个条件，从流量中提出信息，并进行逻辑判断，最终返回一个布尔值（真或假）。

    简单来说，ACL就是if语句中的条件部分。它让HAProxy能够智能地、动态地做出决策，例如：将请求路由到哪个后端、拒绝某个访问、修改请求头等。

    3.2.1.ACL的核心语法

    一条 ACL 规则由两部分组成：一个唯一名称 和 一个匹配条件。

    acl <acl 名称> <匹配条件>
    3.2.2.基于路径的匹配条件
    frontend path
    bind *:80
    acl test1 path_beg -i /static/ /images/     # 以/static/或/images/开头的ACL
    acl test2 path /                            # 路径正好等于/的ACL
    acl test3 path_end -i /login                # 以/login结尾的ACL
    use_backend test1 if test1                  # 若匹配则向test1后端服务器转发
    use_backend test2 if test2
    use_backend test3 if test3

backend test1
    balance roundrobin
    server node1 192.168.80.101:80 check
backend test2
    balance roundrobin
    server node2 192.168.80.102:80 check
backend test3
    balance roundrobin
    server node3 192.168.80.103:80 check
