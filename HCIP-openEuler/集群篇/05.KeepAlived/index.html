    05.KeepAlived

    1.基础原理

    1.1.技术背景

    假设我们搭建了一个电商网站，一开始业务量较小，只有一台服务器对客户提供业务。

    随着我们的业务不断扩大，慢慢的这台服务器已经无法支撑电商网站的流量，随时都有宕机的风险。于是我们决定使用Nginx实现负载均衡功能。

    部署了Nginx实现负载均衡集群后，我们的业务可用性越来越强，能够承受住很高的流量。但是当前所有的流量都需要经过Nginx负载均衡器，Nginx成为了当前的流量瓶颈，且Nginx服务器当前有单点故障的风险，但凡Nginx出现问题无法工作，会直接导致业务中断。

    此时，我们可以增加高可用集群KeepAlived软件加负载均衡集群Nginx作为我们的架构。

    如上图，正常情况下业务流量依旧由master Nginx进程处理，当master Nginx出现故障无法正常使用时，slave Nginx会及时感知并替代master Nginx的工作。

    1.2.KeepAlived是什么？

    Keepalived是Linux下一个轻量级的高可用解决方案，可以实现服务或者网络的高可用。Keepalived提供了兼具负载均衡和高可用性的框架。负载均衡功能使用Linux Virtual Server(IPVS)内核模块，该模块提供第4层负载均衡。

    Keepvalived实现了一组健康检查程序，根据其健康状况动态、自适应维护和管理负载均衡的后端服务器组。高可用性是通过VRRP虚拟路由冗余协议来实现的，VRRP是Keepalived中故障转移的基础。

    Keepalived起初就是为了LVS设计的，专门用来监控后端服务器中各个服务节点的状态，如果某个服务器节点出现故障，Keepalived将自动将节点从调度列表中剔除。当故障节点恢复后，Keepalived会自动将该服务器重新加入到调度列表。

    而VRRP功能则是增强了LVS本身的高可用性，部署多台LVS一台主设备多台备用设备。VIP正常情况下绑定在主用设备的网卡上，由主用设备接收并转发客户请求。备用设备负责通过监听心跳链路及时发现主用设备的状态，一旦主用设备出现故障，则在所有备用设备中选择一台作为新的主用设备接替其工作。

    主要功能：

    • VRRP：让多个服务器共享VIP。主服务器持有这个VIP，备用服务器监视主服务器的状态。一旦主服务器失效，备用服务器自动接管VIP，保证服务的持续性。
    • 健康检查：
    • 负载均衡健康检查：用于定期向后端服务器发送健康检测报文，检测后端服务器状态，决定是否将请求调度到具体的后端服务器。
    • 本机服务的健康检查：用于定期执行管理员配置的脚本，检测当前设备的上层服务状态，用于决定是否降低自身VRRP优先级。
    • 负载均衡：与Linux内核中的IPVS模块结合，提供基于网络层的负载均衡能力，将流量分发到不同的后端服务器上。你可以认为是，Keepalived的出现就是为了弥补LVS不支持健康检测的问题。

    1.3.VRRP协议

    VRRP(Virtual Router Redundancy Protocol)虚拟路由冗余协议，是一种用于提高网络可靠性的容错协议。通过VRRP，可以在主机的下一跳设备出现故障时，及时将业务切换到备份设备，从而保障网络通信的连续性和可靠性。

    1.3.1.概述

    VRRP最早、最常用的场景是在路由器、交换机上使用的，主要是为终端服务。在网络中为了避免单点故障，可以部署多台路由器、多台交换机、堆叠、双机热备、链路聚合等高可用技术，但这些技术是设备或链路高可用。

    如上图，我们平时使用的终端设备想要上网时都必须要有网关，网关指的是距离终端设备最近的三层设备，终端三层互访的流量都必须经过网关进行转发。终端需要在网卡的配置中指定网关的IP地址。

    但是，如果网络中的终端只有一台网关设备，一旦网关设备出现故障，所有终端都无法上网。然而你能想到最简单的方式肯定是再部署一台网关设备，但是这里有一个限制，终端设备的网卡中只能配置一个网关！

    此时，VRRP协议隆重登场，VRRP协议将多台设备组成一个虚拟设备，该虚拟设备拥有自己的虚拟IP地址和虚拟MAC地址（格式：00-00-53-00-01-{VRID}）。所有的内网主机需要将该虚拟IP地址设置为自己的默认网关。

    如下图，组成虚拟设备的两台或多台设备会提前根据规则进行选举，选举出一个Master设备和一个或多个Backup设备。Master设备负责接收所有内网主机的流量承担网关的角色，Master设备真正拥有虚拟IP地址，负责接收并转发内网主机流量。

    而Backup设备负责监听Master设备的状态，一旦Master设备出现故障无法胜任当前工作时，Backup设备便会切换成Master设备，拥有虚拟IP地址，负责接收并转发内网主机流量。

    所以，下图中Router A一开始是Master，当它发生故障后，Router B会第一时间感知到这个变化，并最快速度将虚拟IP地址所承载的流量接收到本端并进行转发。

    1.3.2.状态机

    VRRP协议中定义了三种状态机：初始状态（Initialize）、活动状态（Master）、备份状态（Backup）。其中，只有处于Master状态的设备才可以转发那些发送到虚拟IP地址的报文。下表详细描述了三种状态。

    状态 (State) 说明 (Description)
    Initialize 该状态为VRRP不可用状态，在此状态时设备不会对VRRP通告报文做任何处理。通常设备启动时或设备检测到故障时会进入Initialize状态。
    Master 当VRRP设备处于Master状态时，它将会承担虚拟路由设备的所有转发工作，并定期向整个VRRP备份组内发送VRRP通告报文。
    Backup 当VRRP设备处于Backup状态时，它不会承担虚拟路由设备的转发工作，并定期接受Master设备的VRRP通告报文，判断Master的工作状态是否正常。
    1.3.3.选举机制

    由两台或以上运行了VRRP的设备组成的虚拟设备又称为VRRP备份组。一个VRRP备份组在逻辑上为一台路由器。VRRP备份组建立后（配置完毕），各设备会根据所配置的优先级来选举Master设备，选举方式如下：

    从上图中可看出，VRRP备份组中的所有设备如果优先级未设置为255，默认情况下都会先进入Master状态，然后发送VRRP报文比较优先级，优先级最大的称为Master其他设备成为Backup。如果优先级都相同，则比较接口主IP地址，最大的成为Master。

    其中优先级是一个非常重要的内容，它的取值范围是0 ~ 255。0和255是两个非常特殊的值：

    • 当设备的VRRP优先级设置为255时，跳过选举直接成为当前VRRP备份组的Master。
    • 当设备的VRRP的优先级设置为0时，代表放弃当前Master身份，用来通知备份组中的backup设备。

    如下图，实际上在华为设备中你能够手动配置的VRRP优先级的范围是1-254：

    • 优先级255的情况只会出现在，接口的物理地址和虚拟地址一致的情况下。
    • 优先级0的情况只会出现在，Master设备主动放弃Master的身份的情况，如手动删除VRRP配置。

    1.3.4.备份组

    你可以将VRRP备份组理解成“虚拟路由器团队”，每一个VRRP备份组服务于不同的网段。一个VRRP备份组中会选举出一个Master和多个Backup。由组中的Master设备拥有虚拟IP和虚拟MAC地址的所有权。

    一台VRRP设备上可以配置多个VRRP组，通过VRID这个参数进行区分。不同的VRRP组中的IP地址一定是不同的，根据管理员配置为准。不同的VRRP组中的虚拟MAC地址根据VRID区分，00-00-53-00-01-{VRID}。

    VRID也是管理员手动指定的，用于区分不同VRRP备份组。

    1.3.5.工作原理

    初始化阶段：

    如下图，在VRRP备份组中的多个路由器中，根据选举规则成功选举出Master。Master会立即周期性（默认为1秒）的向VRRP备份组中所有Backup路由器发送VRRP报文，以维持自己Master的身份。

    同时Master会广播发送免费ARP报文，将VRRP备份组的虚拟MAC地址和虚拟IP地址通告给与它连接的交换机。下行的交换机的MAC表项会记录虚拟MAC地址与Master设备端口的对应关系。

    由于内网的PC将网关设置为VRRP备份组的虚拟IP地址，所以当内网PC访问外网产生流量时，首先会广播ARP报文，请求虚拟IP地址对应的虚拟MAC地址。这时只有Master路由器会回应此ARP报文，将虚拟MAC地址回应给PC。

    稳定后的情况：

    当VRRP备份组中Master选举成功后，且已经发送VRRP免费报文，导致交换机和PC都已经成功学习到虚拟MAC地址和虚拟IP地址的对应关系时。

    当PC1需要访问上行流量时，PC会将虚拟MAC地址作为数据包中的目的MAC地址，构建完数据包后将该数据包单播转发给网关（虚拟网关Master）。交换机收到该报文后，查找MAC地址表，发现应该从Ethernet0/0/1接口发出（master）转发给路由器A。

    路由器A收到后，因为自己是Master所以会处理该报文并转发。

    故障的情况：

    如果此时，Master设备出现故障（路由器A的G0/0/0接口断开）时，它将无法发送VRRP报文通知Backup路由器。当Backup路由器在定时器（默认三秒）超时后仍不能收到Master发送的VRRP报文，则认为Master故障，自己切换为Master。

    或者Master主动放弃身份，向Backup发送优先级为0的VRRP报文，此时Backup路由器会立即切换为master，如果有多台backup依旧需要选举。

    VRRP备份组的状态切换完成后，新的Master设备会立即发送携带虚拟IP地址和虚拟MAC地址的免费ARP报文，刷新它与下行设备（交互机）的MAC表项。

    1.3.6.Keepalive中的VRRP

    如上图，这是最基本的Keepalived场景，两台HTTP服务器部署Keepalived，一般我们会在这两台服务器上使用额外的一张网卡充当心跳链路，在心跳链路上两台服务器会进行VRRP的主备选举，随后master设备会在该心跳链路上周期性发送心跳报文，backup设备则在该接口监听master状态。

    根据心跳链路中VRRP的协商结果，master设备会将VIP绑定在自己的网卡上，并发送免费ARP报文声明当前VIP\VMAC与自己的绑定关系，而这个免费ARP实际上是在影响交换机的MAC地址表。此时，客户端向VIP发送的请求报文都会被转发至master设备。

    另外，若你的场景中不方便额外使用网卡作为心跳接口，也可以使用业务网卡作为心跳接口，发送VRRP报文进行选举与维护。

    1.3.7.脑裂

    脑裂指的是由于心跳链路出现故障，备用设备无法感知到主用设备，随即备用设备认为主用设备down机，将VIP绑定在自己的网卡上开始接收客户流量。但实际上此时主用设备依旧正常，就会导致多台设备都绑定VIP。最终出现地址冲突、网络不稳定等情况，导致客户端无法正常访问目标服务。

    脑裂最朴素的解决方法是，增加心跳链路的可用性，比如增加心跳链路的数量，保证VRRP报文在设备之间的畅通。也可以多跟链路进行捆绑实现高可用的心跳链路。

    1.3.8.健康检查

    现在我们可能会产生一个想法，keepalived如果单纯的做高可用没有LVS功能时，是不是我们就不需要它的健康检查功能了，因为没有后端服务器啊，我们只需要通过VRRP报文就可以实现主备检测与切换了。

    这种想法是错误的，在网络世界里的VRRP是给客户端一个IP地址，为它们提供IP转发功能，仅此而已。但是在Keepalived中，我们需要给客户端提供的是服务，不是一个简单的地址。

    举个例子，如果master设备当前的HTTP服务本身出现问题，但是设备依旧正常运转，那么它依旧会周期性向backup设备发送VRRP报文，不会出现主备切换这个动作。那客户端依旧发送的请求会被转发至master，但master此时是没有处理该请求的能力的，导致客户端请求失败。

    所以，此时我们需要的健康检测不是用来检测后端服务器的，而是用来检测自身的。从负载均衡的健康检查转变为本机服务的健康检查。keepalived提供给我们脚本检查机制，它会定期执行我们配置的脚本（vrrp_script）定期检测当前机器的TCP/HTTP服务，一旦检测失败，Keepalived会降低本机的VRRP优先级，触发VRRP抢占功能，backup设备就会接管当前VIP，而本机就会成为backup设备。

    1.4.Keepalived的组成

    Keepalived采用了模块化、事件驱动的设计，清晰地分离了用户空间和内核空间地功能，通过控制平面和数据平面的协同工作，实现了高可用性和负载均衡。

    控制平面：负责解析keepalived.conf配置文件，将配置转化为内部数据结构，分发给各个功能模块，支持动态配置重载（HUP信号）。

    核心调度层：Scheduler架构的“大脑”，基于epoll等机制，统一调度所有I/O事件和定时器事件，协调各模块的异步执行。统一管理内存分配和释放。

    核心组件区：

    • 检查检查子系统（Checkers）：用于定期检查后端或本机的状态，支持TCP/HTTP/HTTPS/SSL/MISC等检查机制。

    • VRRP协议栈（VRRP Stack）：实现VRRP协议，负责主备选举和状态同步。

    • IPVS wrapper：用户空间对IPVS的接口，将配置转换为IPVS规则，如果只做高可用不做LVS，此模块不活跃。

    • 系统调用接口（System call）：用户空间与内核的通用接口，执行网络配置、进程管理等操作。
    • Netlink反射器：专门用于接收内核的网络事件通知，监听接口状态、路由表变化等。
    • SMTP客户端：向管理员发送告警邮件，在状态切换时通知管理员。
    • 看门狗（WatchDog）：监控Keepalived自身进程状态，防止进程僵死。

    内核空间模块：

    • IPVS模块：Linux内核的负载均衡器。
    • NETLINKK接口：用户空间与内核通信的主要机制，用于添加/删除VIP、修改路由表、调整ARP参数，监听网络事件等。

   vrrp_gna_interval 0          # 控制 Keepalived 发送 Gratuitous Neighbor Advertisement（GNA，邻居通告）的间隔时间，单位为秒。 GNA 是一种 IPv6 环境下的广播机制，类似于 ARP 在 IPv4 中的作用，用于通告 IPv6 地址的所有权。 设置 vrrp_gna_interval 为 0 表示不发送 GNA 请求。
}

    vrrp_script chk_nginx {

    rise 1         # 成功次数触发恢复

    1.5.6.TCP_CHECK

    在 Keepalived 中，TCP_CHECK 配置用于对后端服务器执行基于 TCP 的健康检查。它通过建立 TCP 连接来验证后端服务器的可用性和响应性。

    TCP_CHECK 通常配置在 real_server 块中，用于指定检查后端服务器的具体方式。以下是配置的详细说明和示例：

    • connect_ip <IP ADDRESS>: 指定连接的 IP 地址，默认为真实服务器的 IP 地址。
    • connect_port <PORT>: 指定连接的端口，默认为真实服务器提供服务的端口。
    • bindto <IP ADDRESS>: 指定发起连接的源 IP 地址。
    • bind_port <PORT>: 指定发起连接的源端口。
    • connect_timeout <INT>: 连接超时时间，默认为 5 秒。
    • fwmark <INTEGER>: 对检查数据包使用 fwmark 标记。

    • 设置 fwmark 标记，便于通过防火墙规则对检查数据包进行处理。

    • warmup <INT>: 指定随机延迟时间，最大为 N 秒，默认为 0（关闭）。

    • retry <INIT>: 连接失败时的重试次数，默认为 1 次。
    • delay_before_retry <INT>: 重试之前的延迟时间，默认为 1 秒。
    1.5.7.HTTP_CHECK
    • url: 指定要检查的 URL 路径和预期的响应内容。
    • digest: 指定预期响应内容的 MD5 摘要值。
    • connect_timeout <INT>: 设置连接超时时间，默认为 5 秒。
    • send: 发送自定义 HTTP 请求数据。
    • recv: 期望的响应数据。
    • expect: 期望的 HTTP 状态码。
